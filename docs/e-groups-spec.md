## 0. Решения, которые E наследует (не пересматриваются)

- **[У1] Ключ режима — колонка таксономии, не эвристика по названию.**
  Ветка режима выводится **только** из `koilog/taxonomy.py`: `group_of(name)`
  → `Group` (поля `weight_mode`, `timed`, `counts_rm`, `equipment`). Никаких
  `if "жим" in name` внутри агрегатов: забытое ответвление должно быть
  **невозможным**, а не маловероятным.
- **[У2] Кросс-режимные сравнения запрещены**, пока не пререгистрированы явно
  (сейчас — ни одной). Межгрупповые сравнения — только внутри одной ветки и
  одной метрики (см. E3).
- **[У3] `ml_features` не трогается.** `spec_hash` рецепта фич не меняется,
  реплей не нужен; непрерывность лаг-анализа раунда 1 сохраняется. E — **новый
  слой расчёта поверх `load_daily`/`sets`**, а не правка фич.
- **[У4] sRPE/ACWR — запрет впрок.** Источника sRPE нет (нет ручного RPE) →
  ACWR не начинается, пока источник не появился. Тоннажный ACWR как «прокси» —
  запрещён (спорный метод × не те данные).
- **D11-b = A:** нагрузка в **решениях** (gate/state/ramp/plan) не участвует;
  E-слой — аналитика и мониторинг. Формализуется тест-инвариантом (§5).

## 2. E1 — словарь режимов (колонка режима)

**Задача.** Дать **единственный источник** «режим упражнения»: `железо` /
`своё тело` / `кардио`. Не дублировать таксономию, а **вывести** режим из
существующих полей.

**Определение режима (структурное, [У1]):**

| Режим | Условие (по `Group`/`WeightMode`) | Примеры групп |
|---|---|---|
| **кардио** | `group.name == "КАРДИО"` (единственная группа `timed=True, counts_rm=False, equipment="—"`; включает «Разминку», «Бег», «Беговую дорожку») | КАРДИО |
| **своё тело** | `weight_mode_of(name) is not ABSOLUTE` (VEST_ONLY / TOTAL_BODYWEIGHT) и не кардио | ОТЖИМАНИЯ, ПРЕСС, ПОДЪЁМ НОГ, ПЛАНКА, часть ТЯГИ ВЕРТИКАЛЬНОЙ |
| **железо** | `weight_mode is ABSOLUTE` и `not group.timed` | ЖИМ ЛЁЖА, ПРИСЕДАНИЯ, СТАНОВАЯ… |

Порядок проверки: **кардио → своё тело → железо** (кардио первым, т.к. его
`equipment == "—"` иначе не отличить от неопознанного; своё тело — по
`weight_mode_of`, не по группе, чтобы смешанные группы не врали).

**Функция (после одобрения):** `taxonomy.mode_of(name) -> str` (или `Mode`
StrEnum) — **единственная точка**; агрегаты зовут только её.
`mode_of` **выводится кодом** из таксономии, а не хранится ручной колонкой
(ручная колонка рассинхронизируется с `GROUPS`). При первом прогоне — бэкфилл
всей истории (режим считается на лету, материализация не нужна).

**Края:**
- **`UNKNOWN`** (имя не в словаре): режим = `None` (**не** тихий дефолт
  «железо»). Агрегат, встретив `None`, **обязан упасть** (`RuntimeError`) со
  **списком имён-виновников**, а не отнести к ветке. Контроль — существующий
  `taxonomy.unmapped` (печатается при загрузке). Это и есть «невозможное, а не
  маловероятное» [У1].
- **Один режим на упражнение.** Упражнение → **ровно один** режим; попытка
  присвоить два (двухрежимность, напр. «приседания» и железо, и своё тело
  одновременно) — **новая развилка**, оформляется пререгистрацией, а не
  выбирается молча в коде.
- **Смешанная группа** (напр. ПРИСЕДАНИЯ: «штанга / … / своё тело»):
  режим берётся **по конкретному имени** (`weight_mode_of`), не по группе
  целиком — «Приседания» без штанги попадут в ветку верно. Следствие — ключ
  агрегации **(группа × режим)**, см. §2.5.
- **Беговая дорожка** — кардио, тоннаж 0 по построению.

**Тест E1:** синтетика — по одному имени каждой ветки → три разных режима;
неопознанное имя → ошибка **со списком имён**, **не** «железо»; проверка
«упражнение → ровно один режим» (детерминизм `mode_of`).

## 2.5. Ключ агрегации = (группа × режим) — РЕШЕНО: A (Task 27)

**Гейт-стоп исполнения E1.** Бэкфилл режимов по всей истории (боевая база)
дал: неопознанных имён — **0** (таксономия покрывает историю); **17**
однорежимных групп; **3** группы с двумя режимами среди своих имён:
ПРИСЕДАНИЯ (bodyweight/iron), ТРИЦЕПС (bodyweight/iron), ТЯГА ВЕРТИКАЛЬНАЯ
(bodyweight/iron). Двухрежимность — не мусорная: у ПРИСЕДАНИЙ живой железный
ряд (`Приседания с гантелями`, 2026-10-19), у ТЯГИ ВЕРТИКАЛЬНОЙ — живой
телесный (`Подтягивания на перекладине`, 2026-10-08).

**Решение: A — ветка (режим) есть единица агрегации.** Ключ агрегации =
**(группа × режим)**. «Нагрузка ТРИЦЕПСа» — **не число**, а множество режимных
рядов; одного числа не существует.

Аргументы:

1. §2 уже решил: «режим по имени, не по группе» ⟹ ключ = (группа × режим).
   Вариант B (расщепить группу в `GROUPS`) разворачивает решение обратно,
   поднимая ключ с имени на группу.
2. Группа = движение/мышца, режим = свойство измерения — **ортогональные**
   размерности; история честно содержит оба.
3. **Фатальный аргумент против B:** расщепление переписывает `exercise_group`
   в `sets` — ровно тот класс **исторических изменений ряда**, отсутствие
   которого проверялось в `63da8c0`. Создавать такое изменение добровольно —
   нельзя; метрический выигрыш B нулевой (подветки всё равно различаются
   режимом/метрикой). B **отклонён**.

**Пришивка интерфейса (до тестов):**

- **`series(conn, group, mode)` — `mode` обязательный типизированный
  параметр.** Вызов без `mode` = `TypeError`, не молчаливый выбор. Обе
  подветки — два явных вызова (или явный helper-словарь `series_by_mode`).
- **`RuntimeError` выживает только для баг-класса: `mode_of(name) is None`**
  у имени, попавшего в **запрошенную** группу (нарушение инварианта
  таксономии: `group_of` назначил группу, а `mode_of` режима не дал). Остаётся
  громким. Уточнение после A: **смешанность группы — не ошибка** (две явные
  подветки — штатный путь); прежняя формулировка «режим, отличный от режима
  группы» неточна и снята.
- **НОВАЯ ПРОВЕРКА №17: кросс-режимная сумма внутри группы запрещена.**
  «Весь трицепс за неделю» не существует как число. У каждой (группа × режим) —
  своя сетка, своя медиана, свой «мало истории».
- **Мёртвая подветка** не получает вычисленных значений: «—» (одно правило,
  здесь же). В смешанной группе обе подветки **видимы** (живая с числами,
  мёртвая с «—»).
- **Формат E-строки:** (группа, режим) в каждой строке — уже так.

**Живой экспонат анти-эвристики (проверка №3).** `Отжимания на брусьях` —
bodyweight по таксономии, но вес присутствует в **364 из 370** записей. Если бы
режим выводился из наличия веса — фантомный железный тоннаж в E-строке.
**Фикс-тест №3 строить на этом имени.**

**Поправки к приёмочному минимуму.** №6 остаётся **исполняемым** тестом (не «по
построению»): на однорежимной iron-группе **и** на железной подветке смешанной.
№7 (`n_days`) и №10 (сетка) применяются к (группа × режим). **Итого 16 + 1
(№17) = 17 проверок.**

## 3. E2 — погрупповая агрегация (развилка «ноль vs отсутствие»)

**Задача.** Нагрузка **по двигательной группе** (`Group.name`) и **по режиму**
(E1), в окне. **Единица агрегации — (группа × режим)** (§2.5): смешанная
группа даёт по ряду на каждый режим.

**Метрики на ветку [У1]:**

| Режим | Каноническая метрика | Почему |
|---|---|---|
| железо | тоннаж (`SUM(weight*reps)`, `tonnage_iw`) | вес есть |
| своё тело | **подходы** (`sets`) | `weight` пуст/телесный → тоннаж 0 |
| кардио | **время** (`duration_min`) + дистанция | тоннаж 0 |

**Развилка «ноль vs отсутствие» (дневной уровень — ЗАКРЫТ).**
Дневной различитель уже есть: `since_gap`/`gap_warmup` (`load.py`) — «0 тоннажа
в окне простоя» ≠ «0 тоннажа в тренировочный день». Дублировать не нужно.

**Развилка «ноль vs отсутствие» (НЕДЕЛЬНЫЙ уровень — РЕШЕНО: A).**
На неделе строки может не быть вовсе (нет дня) или быть нулевой:

- **Вариант A (РЕШЕНО): «нет данных» ≠ 0.** Пропущенный день/группа в окне →
  агрегат возвращает `None` («не наблюдалось»), а не 0. Сумма по неделе
  считается **только по дням с данными**.
  **Пришивка (два условия):**
  1. `n_days` — **погрупповой** и **всегда рядом со значением** (неделя из
     одного дня видна как тонкая, а не молчаливо усреднена).
  2. **Отдельной константы «минимальный n_days» для агрегата НЕ заводим.**
     Один гейт — только для сравнений (E3-a); `n_days` — **прозрачность, не
     фильтр**.
  Дневной прецедент: пустая неделя, прочитанная как «лёгкая», — фантомный
  сигнал того же класса, что «пустой день = rest».
- **Вариант B (отклонён): 0.** Простой читается как лёгкая неделя — та же
  ошибка, которую `acwr_warmup` починил для ACWR.

**Края E2:**
- **Окно (E2-b, РЕШЕНО: rolling 7).** Окно E = окно `weekly_tonnage`
  **дословно** (те же границы включительности, тот же якорь). Одно определение —
  два потребителя; смена окна = одна правка + тест. Окно **одно для всех трёх
  метрик**, серия **погодичная** (не 7 дискретных слотов).
- **Политика выбросов.** = политика `weekly_tonnage`, где она определена. Для
  веток без политики (время/кардио) — **включаем всё** и **говорим это в
  спеке**; новых тихих фильтров нет (никаких неявных `is_outlier`-отсечений,
  которых нет в `weekly_tonnage`).
- Группа **без 1RM** (`counts_rm=False`: пресс, подъём ног, планка, кардио) —
  метрика = подходы/время, **не** тоннаж; тоннаж там не считается (в базе
  вес не переписывается, см. `etl._finalize`).
- **Тестовый день** (`is_test_day`) — не смешивать с рабочими при агрегации
  (пометка уже в `load_daily`).

**Тест E2:** три группы (железо/своё тело/кардио) на синтетике → разные метрики;
пропущенный день → `None` + корректный погрупповой `n_days`; тонкая неделя
(`n_days=1`) видна как тонкая, не усреднена молча.

## 4. E3 — сравнения балансов (внутри ветки)

**Задача.** Ответить на «антагонисты сбалансированы?» (напр. жим vs тяга,
бицепс vs трицепс) — **исходная цель D11/Round 4**.

**Правило [У2]:** сравнение — **только внутри одной ветки и одной метрики**.
- Жим лёжа (железо, тоннаж) vs тяга горизонтальная (железо, тоннаж) — **можно**.
- Тоннаж груди vs **подходы** кора — **нельзя** (разные метрики + режимы).
- Пресс (своё тело, подходы) vs … — сравнение только с другой группой **той
  же** ветки/метрики.
- **Запрет кросс-метрики — структурный.** Ratio **типизирован веткой**:
  сравнение двух разных типов (напр. `TonnageRatio` vs `SetsRatio`) должно быть
  **ошибкой типов**, а не дисциплиной. Кросс-сравнение, прошедшее типизацию, —
  новая развилка (пререгистрация), не молчаливый дефолт.

**Baseline и выход (РЕШЕНО: N=3, медиана).**
- **Текущее значение:** rolling-7 метрики группы.
- **Baseline:** три **валидных** (не `None`) значения rolling-7, отстоящих от
  текущего на **7 / 14 / 21** — окна **той же ширины**, взаимно не
  перекрываются и с текущим не пересекаются. **Все три обязательны**: частичный
  базлайн **не экстраполируем** — иначе `None` + «мало истории».
- **Статистика базлайна = медиана** трёх значений. Обоснование — **собственный
  лаг-анализ проекта**: среднее тащится больной/обвальной неделей (−0.66 SD на
  лаге 0), медиана из трёх устойчива к одной сумасшедшей неделе. (Если бы в
  спеке стояло среднее — отклонено бы по этому же аргументу.)
- **Выход:** `ratio = текущий rolling-7 / медиана(3 недели)`, единицы —
  **кратность** («1.3× к медиане 3 нед»), **округление 0.1**.

**Пришивка (жёсткая семантика N=3).** N=3 — это **три валидных значения сетки
7/14/21**, а не «3 недели вообще». Цена, фиксируется здесь: после перерыва,
выбивающего сетку, ratio **молчит ~3 недели после возврата** — это **фича**:
сравнения после паузы бессмысленны, возвратом правит **рампа**, не E-строка.

**Края:**
- Нулевой знаменатель → `None`, не деление на 0 и не `inf`.
- Группа с 1–2 валидными значениями базлайна → `None` (не «баланс 3.7×», это шум).
- Кросс-режимное желание («общий объём верха vs низа») **отклоняется** —
  пререгистрированных кросс-режимных конструкций нет [У2].

**Тест E3:** внутри ветки — ratio считается; кросс-метрика — **ошибка типов**;
недостаток валидного базлайна → `None`; медиана устойчива к одной выбросной
неделе (среднее сдвинулось бы — медиана нет).

## 5. E4 — границы дайджеста + тест-инвариант D11-b

**E4: рендер без обхода state.** Дайджест `digest.py` **рендерит** E-строки
**поверх** `state_day` (как уже делает: `load`/`gate`/`state`/`score` — просто
печатаются), **не** меняя решение. Нагрузочная E-строка — **справочная**:
- **E-строка v1 — только описательная:** числа, кратность, `n_days`,
  «мало истории». **Никаких интерпретационных порогов/стрелок/знаков** — порог
  в рендере = контрабанда решения, прямо против E4 «решение не меняет».
- E **не** влияет на рекомендацию (`recommend`), **не** трогает
  `gate.ready`/`state`/`ramp_target` [D11-b=A].
- Если E-агрегата нет (пустая база/нет групп) — строка печатает «нет данных»,
  не падает.

**Файрвол импортов (E4-a, механическая форма D11-b).**
- `state.py` и конвейер меток **не** импортируют `groups.py`.
- `groups.py` **не** импортирует `state.py` (чистый модуль: таксономия +
  нагрузка → агрегаты, без знания о состоянии).
- `digest.py` импортирует **оба** и составляет E-строку поверх `state_day`.
- **Импорт-ассерт — часть инвариант-теста** (проверка `sys.modules`/графа
  импортов, что направления не нарушены).

**Тест-инвариант D11-b (ФЛАГ 1 + ФЛАГ 2, обязателен — в коммит E):**
> **Область: `state.py` + конвейер меток (`ml.build_labels`/метки/`windows`) —
> ноль прямых чтений нагрузочных таблиц (`load_daily`, `srpe`, `tonnage`,
> `acwr`). Фичевый конвейер (`ml.build_features`) исключён по дизайну.**

**Форма проверки — ДВУСТОРОННЯЯ (в одном тесте):**
- **(а) позитивный контроль:** выход E-агрегатов **изменился** — мутация

применилась: сломанная фикстура проходит его триумфально. (а) закрывает этот

**Тест E4:** дайджест с E-строкой → рекомендация **та же**, что без неё

рендер не бросает исключений на пустой базе. **№17:** кросс-режимная сумма

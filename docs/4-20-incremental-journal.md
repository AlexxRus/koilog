## §1 Что делается и что не делается

**П.1 — инкрементальная подгрузка journal.** Добавление опции `--incremental`
в `etl.load_journal()` и в CLI-команду `load` для частичной загрузки journal с
сохранением целостности. Полный режим — дефолт, поведение бит-в-бит; инкремент
— opt-in.

**П.2 — хвостовой файл.** `journal.csv` остаётся каноничным полным (иначе
FeedShrinkError W7 сработает на усохшем каноничном файле, контрольные прогонки
§10.5 завязаны на полный). Частичный экспорт — отдельный файл, например
`journal-incremental-YYYYMMDD.csv`.

**П.3 — дедупликация по БИЗНЕС-ключу.** Дедупликация по БИЗНЕС-ключу (дата; время; упражнение; счётчик подхода в сессии), не по source_row. При совпадении ключа — сверять метрики (reps, weight, time_seconds): несовпадение = отказ, не тихий пропуск.

**П.4 — проверки формы W7.** Все проверки (шапка/12 колонок/даты/порядок/пустоты)
— к куску как к полному фиду; плюс проверка целых сессий: кусок, начинающийся
или кончающийся внутри сессии, — отказ до первой записи.

**П.5 — сообщение о разрыве.** Gap = первая дата куска - последняя дата
тренировок в БД, показывать при >0 с количеством дней — в CLI-вывод (ноутбук
показывает его как есть, отдельной правки ноутбука нет).

**П.6 — отчёт о дубликатах/добавленных.** Информационный вывод в CLI.

**П.7 — откат при частичной записи.** Отказ до первой записи (форма 4-15).

## §2 Ограничения дизайна (семь директив владельца)

1. **Полный режим — дефолт.** `etl.load_journal()` без `--incremental`:
   поведение бит-в-бит с полным файлом `journal.csv`. Инкремент — opt-in.
2. **Дедупликация по БИЗНЕС-ключу.** По (дата; время; упражнение; счётчик
   подхода в сессии) — естественная идентичность строки журнала, устойчивая
   между экспортами. При совпадении ключа — сверять метрики (reps, weight,
   time_seconds): несовпадение = отказ, не тихий пропуск.
3. **Хвостовой файл — отдельный путь.** `journal.csv` остаётся каноничным
   полным (FeedShrinkError W7 §10.5).
4. **Все проверки формы W7.** К куску как к полному фиду (шапка/12 колонок/
   даты/порядок/пустоты); плюс проверка целых сессий: кусок, начинающийся или
   кончающийся внутри сессии, — отказ до первой записи.
5. **Сообщение о разрыве.** Gap = первая дата куска - последняя дата
   тренировок в БД, показывать при >0 с количеством дней через CLI.
6. **Отчёт о дубликатах/добавленных.** Информационный через CLI.
7. **Откат при частичной записи.** Отказ до первой записи (форма 4-15).

## §2.2 Ключ дедупликации

**Бизнес-ключ:** (дата; время; упражнение; счётчик подхода в сессии)
- `date` — колонка 0
- `time` — колонка 1
- `exercise` — колонка 3
- `counter` — порядковый номер подхода в сессии (не в файле!)

**Сверка метрик при совпадении ключа:**
- `reps` — колонка 8
- `weight` — колонка 5 (для упражнений с весом)
- `time_seconds` — колонка 7 (для временных упражнений)

**Правило:** При совпадении ключа — сверять метрики. Несовпадение = отказ,
не тихий пропуск.

Счётчик — по правилу полной загрузки: счётчик подходов per (сессия, упражнение), сессия = (дата; время) (etl _journal_session_id; строки журнала всегда со временем). Кусок обязан содержать целые сессии; кусок, начинающийся или кончающийся внутри сессии, — отказ до первой записи.

## §5 Авто-стоп-чек

**Критерии останова:**
1. Если инкрементальная загрузка изменила хотя бы одну существующую строку
   `sets` (существующие строки бит-в-бит) — стоп.
2. Если инкрементальный режим пропускает проверки формы W7 — стоп.
3. Если `journal.csv` изменяется при инкрементальной загрузке — стоп.
4. Если дедупликация работает не по бизнес-ключу — стоп.
5. Если при совпадении ключа метрики не совпадают и загрузка не отказала — стоп.
6. Если инкрементальный режим принял кусок не из целых сессий — стоп.

**Проверки:**
- Существующие строки `sets` бит-в-бит: полная выгрузка колонок до/после, по
  строкам, которые были в базе до загрузки.
- sha256 файла базы до/после: для тиров-отказов совпадает; для тиров с новыми
  строками файл меняется, и критерий — предыдущий пункт.
- `journal.csv` не изменился (sha256 файла до/после).
- Все проверки формы W7 сработали на куске (§4, тиры 4а).
- Дубликаты определяются по бизнес-ключу, а не по `source_row` (§4, тир 7).
- `git diff --stat` по guarded-путям пуст:

## §6 Разработка (после пререга)

1. **API:**
   - `etl.load_journal(path, body_weight=BODY_WEIGHT, incremental=False)` —
     единственная точка разбора журнала; флаг включает режим куска.
   - `etl._load_incremental(conn, path, body_weight=BODY_WEIGHT)` — план и
     запись куска: план (дедуп, сверка метрик, целые сессии) строится целиком
     до первой записи, отказ не пишет ничего.
   - `etl.check_feed(path, etl.SOURCE_JOURNAL)` — без изменений: кусок
     проверяется существующей функцией формы, флага режима нет (форма у куска
     та же, отдельной функции формы не заводим).

2. **CLI:**
   - `load --incremental PATH` — опция для команды load.
   - Вывод gap/дубликатов через существующий CLI-вывод.

**Не затрагивается:**
- `apple-load` (не входит в скоуп)
- Ноутбуки (NB-98 — отдельная задача)
- `etl.DEFAULT_JOURNAL` — путь к полному файлу
- `etl.WEEKLY_KOI_VIEW` — вид
- `etl.SCHEMA` — схема
- `health.refresh.run()` — конвейер использует полный режим по умолчанию

- Опциональна, полный режим по умолчанию
- Работает только с новым файлом, не изменяет `journal.csv`

- Сообщение о gap (если >0)
- Откат при первой ошибке

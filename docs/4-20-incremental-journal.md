## §1 Что делается и что не делается

**П.1 — инкрементальная подгрузка journal.** Добавление опции `--incremental`
в `etl.load_journal()` и `etl.check_feed()` для частичной загрузки journal с
сохранением целостности. Полный режим — дефолт, поведение бит-в-бит; инкремент
— opt-in.

**П.2 — хвостовой файл.** `journal.csv` остаётся каноничным полным (иначе
FeedShrinkError W7 сработает на усохшем каноничном файле, контрольные прогонки
§10.5 завязаны на полный). Частичный экспорт — отдельный файл, например
`journal-incremental-YYYYMMDD.csv`.

**П.3 — дедупликация по БИЗНЕС-ключу.** По `date;exercise;reps` (не по
`source_row` — физическая строка в частичном экспорте нестабильна).

**П.4 — проверки формы W7.** Все проверки (шапка/12 колонок/даты/порядок/пустоты)
— к куску как к полному фиду.

**П.5 — сообщение о разрыве.** Gap = первая дата куска − последняя дата
тренировок в БД, показывать при >0 с количеством дней — в вывод, попадающий
в ноутбук.

**П.6 — отчёт о дубликатах/добавленных.** Информационный вывод в CLI и
ноутбук.

**П.7 — откат при частичной записи.** Отказ до первой записи (форма 4-15).

## §2 Ограничения дизайна (семь директив владельца)

1. **Полный режим — дефолт.** `etl.load_journal()` без `--incremental`:
   поведение бит-в-бит с полным файлом `journal.csv`. Инкремент — opt-in.
2. **Дедупликация по БИЗНЕС-ключу.** Не по `source_row` (физическая строка
   в частичном экспорте нестабильна), а по `date;exercise;reps`.
3. **Хвостовой файл — отдельный путь.** `journal.csv` остаётся каноничным
   полным (FeedShrinkError W7 §10.5).
4. **Все проверки формы W7.** К куску как к полному фиду (шапка/12 колонок/
   даты/порядок/пустоты).
5. **Сообщение о разрыве.** Gap = первая дата куска − последняя дата
   тренировок в БД, показывать при >0 с количеством дней.
6. **Отчёт о дубликатах/добавленных.** Информационный.
7. **Откат при частичной записи.** Отказ до первой записи (форма 4-15).

## §3 Измерения на живой базе

**Текущее состояние базы (2026-10-31):**
```sql
-- Последняя тренировка в БД
SELECT MAX(date) FROM sets;
-- 2026-10-21

-- Количество записей в sets
SELECT COUNT(*) FROM sets;
-- 15451

-- Количество уникальных дат
SELECT COUNT(DISTINCT date) FROM sets;
-- 1016
```

**Ожидаемые сдвиги при инкрементальной загрузке:**
- Если загрузить кусок с датами `2026-10-22`..`2026-10-27`:
  - Gap = `2026-10-22` - `2026-10-21` = 1 день
  - Новые подходы: ~3-5 (в зависимости от содержимого куска)
  - Дубликатов: 0 (дат нет в БД)
- Если загрузить кусок с датами `2026-10-20`..`2026-10-21`:
  - Gap = 0 (даты уже есть в БД)
  - Дубликаты: все подходы в куске (полное совпадение)
  - Новых подходов: 0

## §4 План тиров

**Тир 1 (минимальный):** Синтетический кусок с 1 новой датой
- Создать `journal-incremental-20261031.csv` с 1 строкой `2026-10-31;...`
- Ожидание: gap=10 дней, 1 новый подход, 0 дубликатов

**Тир 2 (типичный):** Кусок с несколькими новыми датами
- Создать `journal-incremental-20261031.csv` с 3 днями `2026-10-22`..`2026-10-24`
- Ожидание: gap=1 день, 3-5 новых подходов, 0 дубликатов

**Тир 3 (граничный):** Кусок с пересечением существующих данных
- Создать `journal-incremental-20261031.csv` с `2026-10-20`..`2026-10-21`
- Ожидание: gap=0, 0 новых подходов, N дубликатов (N = количество строк в куске)

**Тир 4 (ошибочный):** Кусок с нарушением формы
- Создать `journal-incremental-20261031.csv` с неправильной шапкой
- Ожидание: FeedShapeError как при полном фиде

## §5 Авто-стоп-чек (§9)

**Критерии останова:**
1. Если `etl.load_journal(--incremental)` изменяет существующие данные в БД
   (не допускается) — стоп.
2. Если инкрементальный режим пропускает проверки формы W7 — стоп.
3. Если `journal.csv` изменяется при инкрементальной загрузке — стоп.
4. Если дедупликация работает не по бизнес-ключу — стоп.

**Проверки:**
- Бит-в-бит сравнение `sets` до/после загрузки (кроме новых строк)
- Проверка, что `journal.csv` не изменился
- Проверка, что все проверки формы W7 сработали
- Проверка, что дубликаты определяются по `date;exercise;reps`

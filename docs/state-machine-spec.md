# State-машина возврата: «перерыв → рампа → штатный» (пререгистрация, 5/5a)

Спека **до кода**. Раунд 5 (состояние) + 5a (целевой вес рампы). Образец —
`docs/d10-retro-test.md` и `docs/causal-replay-spec.md`: переходы, критерии и
краевые случаи фиксируются **до** реализации, чтобы выбор нельзя было объяснить
задним числом.

**Контекст.** Причинный ML закрыт (`docs/causal-replay-spec.md` §6): скор —
тихий мониторинг, решения по дням даёт **гейт возврата + окно тишины** (A1/D10)
и **рампа**. Но между «гейт готов» и «по плану» сейчас нет состояния: дайджест
знает только «покой / рампа / можно по плану» как набор условий. Нужна явная
машина состояний — **единственный источник правды** для дайджеста (никаких
рассыпанных `if` в `digest.recommend`, `retrain.return_plan`, CLI).

**Статус:** спецификация зафиксирована и **закрыта** (развилки O1–O3 решены,
A/A/A, §10). Реализация — отдельный раунд; на момент фиксации код не менялся.

## 1. Зачем (что болит)

- `digest.recommend` собирает решение из набора условий (красный флаг → окно
  тишины → активный эпизод → простой → «по плану»). Работает, но решение
  «размазано»: негде показать «идёт 5-й день рампы, цель — 8×40».
- `retrain.baseline_gate` + `window_only` уже дают «можно ли», но не «как».
- 5a: **целевой вес** рампы должен считаться по 1RM **до болезни**
  (существующая логика `core.one_rm`/`stats.progression_from_db`, см. §6), а не
  выдумываться в дайджесте.

## 2. Состояния (зафиксировано)

Ровно четыре, в порядке приоритета (первое подходящее побеждает):

| Состояние | Когда | Смысл |
|---|---|---|
| `sick` | активный эпизод (`illness.build`: сегодня внутри `[start, end]`) или красный флаг (t запястья ≥ порога) | не тренироваться по плану |
| `rest` | гейт не готов и причина **не** окно тишины (каналы держат: `rhr_z`/`hrv_z` две ночи, либо t) | покой, ждать |
| `ramp` | гейт не готов **из-за окна тишины** (`gate.window_only`) **или** окно прошло, но простой ≥ порога и рампа не завершена | осторожный возврат |
| `normal` | гейт готов и простой < порога (или рампа завершена и ничего не мешает) | штатный план |

**Приоритет:** `sick` > `rest` > `ramp` > `normal`. Порядок важен: эпизод
посреди рампы возвращает в `sick` (см. §5), а не оставляет «рампу с болезнью».

## 3. Переходы (зафиксировано)

```
normal --(эпизод / красный флаг)--> sick
sick   --(эпизод кончился)--------> ramp      # первый день возврата
ramp   --(гейт не готов, не окно)-> rest      # каналы ещё держат
rest   --(гейт готов / окно-------> ramp
ramp   --(RAMP_DAYS выполненных дней)-> normal
любое  --(новый эпизод)-----------> sick      # в т.ч. ramp/normal
```

Критерии входа/выхода — **только из существующих функций**:

- **Вход в `ramp`** (`entered_ramp`):
  - `gate.window_only` истинно (окно тишины 14 дн после эпизода), **или**
  - простой (нет тренировок) ≥ `RAMP_GAP_DAYS` (см. §4), и гейт не «rest».
- **Выход из `ramp` в `normal`**: рампа прожита `RAMP_DAYS` **выполненных** дней
  (см. §5.1 про семантику `k`) **и** последний день рампы гейт готов
  (`gate.ready`).
- **Возврат в `rest`**: внутри рампы гейт стал не готов **не** по окну тишины
  (каналы держат) — рампа **приостанавливается, не сбрасывается**: счётчик `k`
  сохраняется, дни `rest` его не увеличивают. Безопасно это ровно потому, что
  гейт страхует **каждый** день рампы: пауза — не «потерянный день», а день,
  закрытый тем же односторонним гейтом (D10).
- **Гистерезис:** состояние не пересчитывается от «сегодня легко» —
  `ramp → normal` только по **выполненным** дням, не по одному хорошему дню.
  Обратный переход `normal → ramp` — только через `sick` или простой, не по
  одному плохому дню (гейт для того и односторонний, D10).

## 4. Константы (пререгистрация, до подбора)

- `RAMP_DAYS = 5` — длина рампы (**выполненных** дней возврата, см. §5.1).
  Обоснование: окно тишины 14 дн (D10) — это **допуск** к нагрузке, а не сама
  рампа; 5 дней — минимальная рампа, которая уже не «два дня и по плану».
  Длительность болезни в системе **уже закодирована** окном тишины (14 дн
  якорены к эпизоду), поэтому отрыв от тренировок масштабируется с болезнью
  автоматически — рампа не кодирует тот же сигнал второй раз. Её работа —
  безопасный вход; восстановление силы — работа штатной прогрессии (детрейн
  возвращается обычными шагами, рампа не компенсирует детрейн). Значение
  фиксируется до прогона, изменение — новый `SPEC_VERSION` состояния.
- `RAMP_DAYS` живёт **именованной константой** рядом с логикой возврата
  (модуль состояния), **не** магическим числом в `digest`.
- **Fallback O1** (пререгистрирован, **проспективный триггер**): если после
  выхода в `normal` рецидивы/срывы будут концентрироваться в первые 7 дней →
  возврат к развилке O1 под новым `spec_hash` (вариант «длина рампы от
  длительности эпизода»). Ретро-тест на исторических возвратах для этого
  маломощен: рецидивы конфаундены кластерами и их закрывает окно тишины, а не
  рампа. Триггер — только проспективные исходы, не подгонка под историю.
- `RAMP_GAP_DAYS = 7` — простой, после которого штатный план уже не «штатный»
  (совпадает с горизонтом `H_ONSET`; тот же масштаб, что у ML-ламбды).
- Пороги каналов **не трогаются** — `Z_CHANNEL = 1.5` в дайджесте, `GATE_Z` в
  гейте остаются как есть (A1/D10 не пересматривается).

## 5. Краевые случаи (зафиксировано)

1. **Новый эпизод посреди рампы.** `sick` перебивает: день рампы не считается
   прожитым, счётчик рампы **сбрасывается** (после болезни рампа начинается
   заново — иначе возврат после двух болезней подряд был бы «на второй день»).
   **Семантика `k` (доколочено до кода):** `k` — число **выполненных** дней
   рампы (сессия по плану состоялась), **не** календарных. День, заблокированный
   гейтом (`rest`) или просто без сессии, `k` не увеличивает. `sick` = сброс,
   `rest` = пауза; различие механическое (эпизод есть в базе vs просто gap), без
   ручного ввода.
2. **Рампа и «простой» одновременно.** Если после эпизода рампа завершена, но
   простой всё ещё ≥ `RAMP_GAP_DAYS` (человек не тренировался) — остаёмся в
   `ramp` до первого тренировочного дня либо до `RAMP_DAYS` **выполненных**
   дней, смотря что позже. Причина: «прожил 5 дней» без нагрузки ≠ возврат. Это
   следствие §5.1: незавершённая рампа не может закрыться календарём.
3. **Пауза в `rest` при незавершённой рампе.** Счётчик `k` сохраняется, но
   **число не показывается** — строка `рампа приостановлена` без «день 3 из 5».
   Снимает вопрос «почему снова день 3?» и не создаёт тикающего счётчика в
   `rest`/`sick`.
3. **Данные кончились (сегодня = последний день ряда).** Состояние считается на
   дату; отсутствие `aw_daily` за сегодня не делает `sick`/`rest` — опираемся на
   последний доступный день (как `day_state`).
4. **Гейт не построен (нет данных вовсе** — чистый клон). Состояние `normal`
   без рампы: рампа не выдумывается из пустоты; `reason = "нет данных"`.
5. **Первый день истории.** Прошлого нет → `normal` (не `ramp`): рампа — про
   **возврат**, а не про старт.
6. **Строка скора в каждом состоянии.** Скор — **мониторинг** (после causal
   replay). Рендер:
   - `sick`: `скор (причинный): 0.72 — в эпизоде, скор не решает`
   - `rest`: `скор (причинный): 0.72 — мониторинг (порог 0.90), решение — покой`
   - `ramp`: `скор (причинный): 0.72 — мониторинг (порог 0.90), решение — рампа`
     (+ `рампа: день k из 5`, только когда рампа идёт и видна)
   - `rest` при незавершённой рампе: `… решение — покой (рампа приостановлена)`
   - `normal`: как сейчас, `мониторинг (порог 0.90)`.
   То есть скор **не** меняет состояние ни в одном случае — только поясняет.

## 5-бис. Sick-tail: sick снимается только чистым гейтом (раунд 6)

**Повод (зафиксирован как есть, без подгонки).** Живой кейс 19–20.10.2026:
эпизод 34 размечен **одним днём** (19.10, `probable`; RHR z +4.4 при **ВСР в
фоне** — рибаунд-маскировка). Проверка «активный эпизод» в гейте — точная по
дате (`start <= d <= end`), поэтому 20.10 эпизод уже «не активен», и
`state_day` отдаёт `rest` **только потому, что гейт ещё держит RHR**. Если бы
физиология нормализовалась раньше разметки, машина сказала бы `normal` посреди
болезни. Дыра классовая: **разметка короче деривации**, а защищает только
односторонний гейт, стоящий в приоритете **ниже** `sick`.

**Почему не правим разметку (`illness.py`).** Спан эпизодов входит в метки
(`ml_labels`), catchable/nowcast, окна тишины и все числа отчёта — это
C12-класс с полным перегоном. Эп-34 — первый задокументированный кейс; решение
по спанам примем по накопленной живой статистике (отдельный пререгистрированный
раунд). Здесь закрываем **правило снятия `sick`**, не разметку.

**Определение (рекурсивное, реализуется обратным сканом от `d`):**

```
sick(d)      = эпизод_активен(d) ∨ красный_флаг(d) ∨ sick_tail(d)
sick_якорь(a)= эпизод_активен(a) ∨ красный_флаг(a) ∨ sick_tail(a)
sick_tail(d) = ∃ a < d: sick_якорь(a) ∧ ∀ t ∈ (a, d]: гейт_держит_по_каналам(t)
               ∨ гейт_неоцениваем(t)
```

Обратный скан идёт от `d` назад; стоп — на первом **чистом** дне
(`гейт(t)` оценён и проходит по каналам) или на глубине `SICK_TAIL_MAX`. Скан
**stateless** (только данные дня), детерминизм сохраняется.

**Пять правил:**

1. **Снятие — только положительное чистое свидетельство.** Гейт оценён и
   проходит по каналам (две чистые ночи — гистерезис уже встроен в гейт).
   **«Нет данных ≠ чисто»:** неоцениваемый гейт (ночей нет / фон не набран)
   sick **не снимает** — иначе хвост пробивается любым гэпом данных, а их много
   (t запястья ~85 % пропусков). «Держит по каналам» = в причинах гейта нет
   ни одного канального пункта (`RHR z`, `ВСР z`, `t запястья`) — окно тишины
   и «нет фона» канальными не считаются.
2. **Окно тишины («держит» не по каналам) хвост не продлевает**:
   `window_only` = каналы чисты = снятие. Хвост держит именно **канальная**
   деривация, не календарь окна.
3. **Незаякоренный дериваж → `rest`, не `sick`.** Гейт держит, но эпизода/флага
   до дня не было — это усталость/перерыв, не болезнь (защита стрик-17: длинный
   плохой период без эпизода не должен стать «болезнью»). Хвост только
   **продлевает** существующий `sick`, новый не создаёт.
4. **Якорь рампы после `sick` = последний `sick`-день** (разметка или хвост) →
   после болезни `k = 0` автоматически. Для чистых случаев (эп-33: 3 дня,
   каналы чисты) якорь совпадает со старым — тесты раунда 5 не ломаются.
5. **Приоритет не меняется** (`sick > rest > ramp > normal`), меняется только
   определение `sick`. Константа `SICK_TAIL_MAX = 7` (тот же масштаб, что
   `RAMP_GAP_DAYS`/`H_ONSET`) — предохранитель от неограниченного скана.

**`SICK_TAIL_MAX = 7` — что именно она ограничивает (уточнено при коммите
раунда 6, политическая константа в критическом пути).** Константа задаёт
**глубину обратного скана**, а не «время жизни хвоста»: `sick_tail(d)` ищет
якорь не дальше `7` дней назад. Следствие (проверено синтетикой: якорь 10.01,
непрерывный дериваж до 25.01): хвост держится `11…16.01` (6 дней = `MAX − 1`),
а **17.01 становится `rest`, не `normal`** — якорь вышел за горизонт скана,
гейт ещё держит, а незаякоренный дериваж по правилу 3 = «усталость/перерыв»,
не болезнь. То есть демоция дня `MAX + 1` при непрерывном гейте **не может**
дать `normal`: её ловит правило 3. Второе прочтение («хвост живёт ровно `MAX`
дней после якоря») описывает тот же код, но менее точно — поэтому канон здесь
«глубина скана».

**Арифметика вслух (чтобы «7» не прочитали как «7 дней хвоста»):** якорь дня
`a` виден скану от `d`, пока `d − a ≤ 6`; при `d − a = 7` якорь ровно на
границе и **вне** горизонта (`checked < SICK_TAIL_MAX` даёт 7 итераций от `d`
включительно: `d, d−1, …, d−6`). Значит **хвост держит не более 6 дней после
якоря**; «7» — глубина скана, а не срок жизни. Тест `test_tail_scan_is_bounded`
прибит к этой арифметике (`MAX − 1` дней — ещё tail, `MAX` — уже `rest`).

*Почему 7.* Тот же масштаб, что `RAMP_GAP_DAYS = 7` и горизонт метки
`H_ONSET = 7`: болезнь дольше недели держит гейт сама (дериваж), якорь нужен
лишь как «спусковой крючок» продления. *Цена ограничения:* настоящая болезнь
длиной > 7 дней с непрерывной деривацией после короткой разметки теряет метку
`sick` на 8-й день и показывается как `rest` — **решение дня почти то же**
(покой), отличается только метка, приоритет и `k`. Это осознанный компромисс:
неограниченный скан тянул бы всю историю каналов на каждый день, а «покой vs
sick» в 8-й день непрерывной деривации лечит гейт, не ярлык.

**По схеме:** 20.10 = `sick` (якорь 19.10, каналы дериваны) ✓; при двух чистых
ночах → снятие → `ramp` (окно тишины эп-34 до ~02.11) ✓; незаякоренный дериваж
→ `rest` ✓. Честную строку живого кейса в README обновить
(«разметка 1 день, хвост закрыл 20.10»).

**Остаточная дыра (известный риск, детектора нет):** гейт чист ≥ 2 ночей
из-за рибаунд-маскировки **и** разметка короткая **и** за пределами окна тишины
→ `normal`. Кандидат на закрытие — отдельный пререгистрированный раунд по
**спану эпизодов** в `illness.py`; эп-34 — его первый кейс.

### Дополнение от 20.10.2026 (спустя сутки, **append-only**)

**Факт ревизии данных.** Выгрузка 20.10 (09:28) принесла **уточнённые** ночные
метрики за 19.10: RHR **73** (в момент фиксации §5-бис было 83), ВСР **65**
(было 98). Причина ревизии — Apple пересчитывает ночные агрегаты задним числом
(`creationDate` записи RHR за 19.10 = `2026-10-19 23:08`). `refresh`
перезаписал `aw_daily`, `illness.build` пересчитал разметку, и **эпизод 34
снят**: `RHR z` упал с +4.4 до +1.8, «одиночный сильный сигнал» исчез —
разметка честно убрала эпизод, которого больше нет в данных.

**Что это значит.**

1. **Наблюдение §5-бис остаётся как записано — оно было честным на момент T.**
   Это не ошибка и не подгонка: живое решение (sick 19.10, удержание гейта
   20.10, скор 0.84→0.70) принято **по значениям 83/98** и валидно *по данным
   на момент T* — причинная рамка проекта (ledger `ml_score`) это уже
   закрепила. Ревизия данных — системный факт, а не мусор; **наблюдения —
   append-only** (как `ml_score`), поэтому дописываем, а не стираем.
2. **Класс отказа «разметка короче деривации» не отменяется.** Он не был
   свойством конкретного эп-34 — он классовый: проверка «активный эпизод»
   точная по дате, а деривация может быть длиннее разметки. Живой кейс исчез
   из базы, но правило снятия `sick` нужно ровно так же.
3. **Единственная улика — этот документ и тест-реплика.** После ревизии в базе
   улики нет. Чтобы раунд 6 не остался без воспроизводимого мотива, в тесты
   кладётся **синтетическая реплика эп-34** с сохранёнными числами момента
   фиксации (RHR 83 / ВСР 98, эпизод одним днём): хвост держит 11–12.01,
   снимается двумя чистыми ночами (13.01 → `ramp`).
4. **Фактический статус 19–20.10 на текущих данных** (для README/дайджеста):
   эпизода нет, 19.10 каналы держат (`RHR z +1.8`) без якоря → `rest`
   (спека п.3, незаякоренный дериваж). Это **корректное** поведение машины на
   уточнённых данных, а не регресс: хвост не создаёт `sick` из ничего.

**Правило не меняется ни на строку.** Дополнение — про данные и
воспроизводимость, не про логику: пп. 1–5 выше остаются в силе.

## 6. 5a: целевой вес рампы (зафиксировано)

- Целевой вес — **вес по 1RM до болезни**, а не «процент от вчерашнего».
  Логика — **существующая**, не дублировать. Точные имена (проверены по коду):
  - `koilog/core.py`: `one_rm(weight, reps)` — оценка 1RM (Epley-подобная),
    `rm_factor(reps)`, `next_weight(weight, available, hands=1)` — шаг к
    ближайшему доступному весу, `progression(...)` — прогрессия по прошлому;
  - `koilog/stats.py`: `available_weights(...)` — стек веса под упражнение,
    `progression_from_db(...)` / `progression_from_available(...)` —
    прогрессия на реальных данных;
  - `koilog/equipment.py`: `weights_of(...)`, `available_weights(...)`,
    `in_stock(...)` — стек оборудования (гантели/штанга, шаги грифа);
  - `koilog/health/load.py`: `rm_regress(rm_best)` — динамика 1RM по дневным
    лучшим (уже используется в нагрузке).
- 1RM «до болезни» — по последнему тренировочному дню перед `start` эпизода:
  лучший `one_rm` за день. Готовое брать готовым: дневной лучший уже лежит в
  `load_daily.rm_best` (`koilog/health/load.py:445`, `MAX(rm_session)` по дню), а
  по упражнению/периоду — `stats.py` (`best_rm`, `best_day`, `prev_rm`,
  `rm_delta`). Новую агрегацию не писать.
- Вывод 5a в дайджесте — **справочный**: `цель рампы: 8×40 (по 1RM 50 до
  18.11, шаг 2.5)`. Если 1RM до болезни нет — `цель: без 1RM, по прошлой
  сессии` (через `progression_from_db`).
- **Округление — `floor` (O2), и это структурное поле плана, не текст.**
  Производный вес = ближайший доступный **ниже** «положенного» по 1RM. Пометка
  живёт в плане как поле (`rounding: "floor"` / `rule: "ramp_floor"`), дайджест
  рендерит её **механически** — так тест проверяет поле, а не строку вывода.
  - Цена асимметрична и мала: продолжая от последнего **выполненного** дня
    рампы, `normal` догоняет штатным шагом за один день (40 → 45). Ошибка
    вверх (45 в первый день возврата после 3+ недель off) дороже.
  - Floor применяется **единообразно к производному весу каждого дня рампы**;
    после рампы `normal` продолжает **от последнего выполненного дня рампы**.
  - **Краевой:** производный вес ниже минимума стека —
    `core.snap_to_ladder` возвращает `None` (ни один снаряд не легче
    записанного). Практически недостижимо (1RM оценивается из выполненных
    весов); `ramp_target` тогда отдаёт «без 1RM, по прошлой сессии», а не
    выдумывает минимум. Спека не молчит и **не обещает** подстановку минимума:
    это было бы домыслом о данных.
- 5a **не** меняет состояние: вес — подсказка внутри `ramp`.

## 7. Единственный источник правды (зафиксировано)

- Новая функция `state_day(conn, day) -> StateDay` в `koilog/health/digest.py`
  (или новый `state.py`, если так чище слоями; решает реализация, но **одно**
  место): состояние, причина, день рампы, цель рампы.
- `digest.recommend` **перестаёт** собирать решение из условий сам: читает
  `state_day` и рендерит текст. Никаких рассыпанных conditionals.
- `retrain.baseline_gate` остаётся **входом** машины (готов/не готов, окно
  тишины, причины) — не дублируется и не ослабляется.
- Правило #0 (раунд 6) целиком ложится на state: «что сегодня» = `state_day`
  + дайджест, без ML-веток.

## 8. Критерий приёмки (зафиксирован заранее)

1. Состояние — **функция** дня и данных (детерминированная, без истории
   запусков): повторный расчёт того же дня даёт то же состояние.
2. Переходы §3 воспроизводятся на синтетике: `sick → ramp → normal`;
   `ramp → rest → ramp`; `sick` посреди рампы сбрасывает счётчик (§5.1).
3. Скор **не** влияет на состояние ни в одном тесте (меняем скор — состояние
   неизменно).
4. Дайджест печатает состояние и строку скора по §5.6; строка «мониторинг
   (порог …)» — из этого раунда, не решающая.
5. 5a: целевой вес совпадает с логикой `core`/`stats` на фикстурах (не
   дублирующая арифметика); без 1RM — «по прошлой сессии»; **floor прибит
   тестом** на синтетическом стеке (1RM ⇒ 42 ⇒ 40) — чтобы через полгода никто
   не «починил» молча на nearest.
6. Никаких новых порогов каналов: A1/D10 не пересматривается (кроме констант
   `RAMP_DAYS`/`RAMP_GAP_DAYS` из §4).
7. **Семантика `k`:** `ramp → rest → ramp` сохраняет счётчик (пауза не сброс),
   `sick` посреди рампы сбрасывает; `rest` при незавершённой рампе печатает
   «рампа приостановлена» без числа. Это два места, где семантику `k` можно
   сломать незаметно — тесты обязательны.

## 9. Граница раунда (что НЕ трогается)

- ML-ветка закрыта: `walk_forward`, ledger, `ml_score` — как есть (мониторинг).
- Гейт A1/D10 и окно тишины 14 дн не пересматриваются.
- Тоннаж/атрибуция (D11, E) — другие ветки, здесь не считаются.
  **D11 вынесен в пререгистрацию** — `docs/d11-load-input.md` (канонический вход
  нагрузки + роль нагрузки в решениях); заполняет ссылку, которая раньше висела.

## 10. Решения по развилкам (закрыто: A/A/A)

- **O1 → A.** `RAMP_DAYS = 5` фиксированные, **выполненных** дней (§4).
  Вариант «по длительности эпизода» — **пререгистрированный fallback** с
  **проспективным** триггером (рецидивы в первые 7 дней после выхода в `normal`
  → возврат под новым `spec_hash`), не ретро-тест. Основание: длительность
  эпизода артефакт-чувствительна (группировка gaps в `illness.py`) — связывать
  с ней предсказуемую state-машину нельзя; окно тишины уже масштабирует отрыв
  от тренировок с болезнью.
- **O2 → A.** Округление **вниз** (`floor`) структурным полем плана, тест
  прибивает floor на синтетическом стеке (§6). Цена — одна ступень на первом
  штатном дне; ошибка вверх дороже. Краевой: ниже минимума стека → минимум.
- **O3 → A.** «День `k` из 5» показывается явно — но `k` = **выполненные** дни
  (§5.1), в `rest`/`sick` число не показывается (`рампа приостановлена`),
  счётчик при паузе сохраняется. Обоснование паузы без сброса: гейт страхует
  каждый день рампы, пауза — не потерянный день, а день, закрытый D10-гейтом.

Пререгистрация закрыта: реализация раунда 5+5a идёт поверх этих решений без
дальнейших развилок.

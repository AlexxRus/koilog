# State-машина возврата: «перерыв → рампа → штатный» (пререгистрация, 5/5a)

Спека **до кода**. Раунд 5 (состояние) + 5a (целевой вес рампы). Образец —
`docs/d10-retro-test.md` и `docs/causal-replay-spec.md`: переходы, критерии и
краевые случаи фиксируются **до** реализации, чтобы выбор нельзя было объяснить
задним числом.

**Контекст.** Причинный ML закрыт (`docs/causal-replay-spec.md` §6): скор —
тихий мониторинг, решения по дням даёт **гейт возврата + окно тишины** (A1/D10)
и **рампа**. Но между «гейт готов» и «по плану» сейчас нет состояния: дайджест
знает только «покой / рампа / можно по плану» как набор условий. Нужна явная
машина состояний — **единственный источник правды** для дайджеста (никаких
рассыпанных `if` в `digest.recommend`, `retrain.return_plan`, CLI).

**Статус:** спецификация зафиксирована, реализация — отдельный раунд. Код не
менялся.

## 1. Зачем (что болит)

- `digest.recommend` собирает решение из набора условий (красный флаг → окно
  тишины → активный эпизод → простой → «по плану»). Работает, но решение
  «размазано»: негде показать «идёт 5-й день рампы, цель — 8×40».
- `retrain.baseline_gate` + `window_only` уже дают «можно ли», но не «как».
- 5a: **целевой вес** рампы должен считаться по 1RM **до болезни**
  (существующая логика `koilog/training.py`), а не выдумываться в дайджесте.

## 2. Состояния (зафиксировано)

Ровно четыре, в порядке приоритета (первое подходящее побеждает):

| Состояние | Когда | Смысл |
|---|---|---|
| `sick` | активный эпизод (`illness.build`: сегодня внутри `[start, end]`) или красный флаг (t запястья ≥ порога) | не тренироваться по плану |
| `rest` | гейт не готов и причина **не** окно тишины (каналы держат: `rhr_z`/`hrv_z` две ночи, либо t) | покой, ждать |
| `ramp` | гейт не готов **из-за окна тишины** (`gate.window_only`) **или** окно прошло, но простой ≥ порога и рампа не завершена | осторожный возврат |
| `normal` | гейт готов и простой < порога (или рампа завершена и ничего не мешает) | штатный план |

**Приоритет:** `sick` > `rest` > `ramp` > `normal`. Порядок важен: эпизод
посреди рампы возвращает в `sick` (см. §5), а не оставляет «рампу с болезнью».

## 3. Переходы (зафиксировано)

```
normal --(эпизод / красный флаг)--> sick
sick   --(эпизод кончился)--------> ramp      # первый день возврата
ramp   --(гейт не готов, не окно)-> rest      # каналы ещё держат
rest   --(гейт готов / окно-------> ramp
ramp   --(N дней рампы прожиты)---> normal
любое  --(новый эпизод)-----------> sick      # в т.ч. ramp/normal
```

Критерии входа/выхода — **только из существующих функций**:

- **Вход в `ramp`** (`entered_ramp`):
  - `gate.window_only` истинно (окно тишины 14 дн после эпизода), **или**
  - простой (нет тренировок) ≥ `RAMP_GAP_DAYS` (см. §4), и гейт не «rest».
- **Выход из `ramp` в `normal`**: рампа прожита `RAMP_DAYS` дней (см. §4) **и**
  последний день рампы гейт готов (`gate.ready`).
- **Возврат в `rest`**: внутри рампы гейт стал не готов **не** по окну тишины
  (каналы держат) — рампа приостанавливается, не сбрасывается.
- **Гистерезис:** состояние не пересчитывается от «сегодня легко» —
  `ramp → normal` только по прожитым дням, не по одному хорошему дню. Обратный
  переход `normal → ramp` — только через `sick` или простой, не по одному
  плохому дню (гейт для того и односторонний, D10).

## 4. Константы (пререгистрация, до подбора)

- `RAMP_DAYS = 5` — длина рампы (дней возврата). Обоснование: окно тишины 14 дн
  (D10) — это **допуск** к нагрузке, а не сама рампа; 5 дней — минимальная
  рампа, которая уже не «два дня и по плану». Значение фиксируется до прогона,
  изменение — новый `SPEC_VERSION` состояния.
- `RAMP_GAP_DAYS = 7` — простой, после которого штатный план уже не «штатный»
  (совпадает с горизонтом `H_ONSET`; тот же масштаб, что у ML-ламбды).
- Пороги каналов **не трогаются** — `Z_CHANNEL = 1.5` в дайджесте, `GATE_Z` в
  гейте остаются как есть (A1/D10 не пересматривается).

## 5. Краевые случаи (зафиксировано)

1. **Новый эпизод посреди рампы.** `sick` перебивает: день рампы не считается
   прожитым, счётчик рампы **сбрасывается** (после болезни рампа начинается
   заново — иначе возврат после двух болезней подряд был бы «на второй день»).
2. **Рампа и «простой» одновременно.** Если после эпизода рампа завершена, но
   простой всё ещё ≥ `RAMP_GAP_DAYS` (человек не тренировался) — остаёмся в
   `ramp` до первого тренировочного дня либо до `RAMP_DAYS` прожитых дней,
   смотря что позже. Причина: «прожил 5 дней» без нагрузки ≠ возврат.
3. **Данные кончились (сегодня = последний день ряда).** Состояние считается на
   дату; отсутствие `aw_daily` за сегодня не делает `sick`/`rest` — опираемся на
   последний доступный день (как `day_state`).
4. **Гейт не построен (нет данных вовсе** — чистый клон). Состояние `normal`
   без рампы: рампа не выдумывается из пустоты; `reason = "нет данных"`.
5. **Первый день истории.** Прошлого нет → `normal` (не `ramp`): рампа — про
   **возврат**, а не про старт.
6. **Строка скора в каждом состоянии.** Скор — **мониторинг** (после causal
   replay). Рендер:
   - `sick`: `скор (причинный): 0.72 — в эпизоде, скор не решает`
   - `rest`: `скор (причинный): 0.72 — мониторинг (порог 0.90), решение — покой`
   - `ramp`: `скор (причинный): 0.72 — мониторинг (порог 0.90), решение — рампа`
   - `normal`: как сейчас, `мониторинг (порог 0.90)`.
   То есть скор **не** меняет состояние ни в одном случае — только поясняет.

## 6. 5a: целевой вес рампы (зафиксировано)

- Целевой вес — **вес по 1RM до болезни**, а не «процент от вчерашнего».
  Логика — **существующая**, не дублировать. Точные имена (проверены по коду):
  - `koilog/core.py`: `one_rm(weight, reps)` — оценка 1RM (Epley-подобная),
    `rm_factor(reps)`, `next_weight(weight, available, hands=1)` — шаг к
    ближайшему доступному весу, `progression(...)` — прогрессия по прошлому;
  - `koilog/stats.py`: `available_weights(...)` — стек веса под упражнение,
    `progression_from_db(...)` / `progression_from_available(...)` —
    прогрессия на реальных данных;
  - `koilog/equipment.py`: `weights_of(...)`, `available_weights(...)`,
    `in_stock(...)` — стек оборудования (гантели/штанга, шаги грифа);
  - `koilog/health/load.py`: `rm_regress(rm_best)` — динамика 1RM по дневным
    лучшим (уже используется в нагрузке).
- 1RM «до болезни» — по последнему тренировочному дню перед `start` эпизода:
  лучший `one_rm` за день. Готовое брать готовым: дневной лучший уже лежит в
  `load_daily.rm_best` (`koilog/health/load.py:445`, `MAX(rm_session)` по дню), а
  по упражнению/периоду — `stats.py` (`best_rm`, `best_day`, `prev_rm`,
  `rm_delta`). Новую агрегацию не писать.
- Вывод 5a в дайджесте — **справочный**: `цель рампы: 8×40 (по 1RM 50 до
  18.11, шаг 2.5)`. Если 1RM до болезни нет — `цель: без 1RM, по прошлой
  сессии` (через `progression_from_db`).
- 5a **не** меняет состояние: вес — подсказка внутри `ramp`.

## 7. Единственный источник правды (зафиксировано)

- Новая функция `state_day(conn, day) -> StateDay` в `koilog/health/digest.py`
  (или новый `state.py`, если так чище слоями; решает реализация, но **одно**
  место): состояние, причина, день рампы, цель рампы.
- `digest.recommend` **перестаёт** собирать решение из условий сам: читает
  `state_day` и рендерит текст. Никаких рассыпанных conditionals.
- `retrain.baseline_gate` остаётся **входом** машины (готов/не готов, окно
  тишины, причины) — не дублируется и не ослабляется.
- Правило #0 (раунд 6) целиком ложится на state: «что сегодня» = `state_day`
  + дайджест, без ML-веток.

## 8. Критерий приёмки (зафиксирован заранее)

1. Состояние — **функция** дня и данных (детерминированная, без истории
   запусков): повторный расчёт того же дня даёт то же состояние.
2. Переходы §3 воспроизводятся на синтетике: `sick → ramp → normal`;
   `ramp → rest → ramp`; `sick` посреди рампы сбрасывает счётчик (§5.1).
3. Скор **не** влияет на состояние ни в одном тесте (меняем скор — состояние
   неизменно).
4. Дайджест печатает состояние и строку скора по §5.6; строка «мониторинг
   (порог …)» — из этого раунда, не решающая.
5. 5a: целевой вес совпадает с `training.py` на фикстурах (не дублирующая
   арифметика); без 1RM — «по прошлой сессии».
6. Никаких новых порогов каналов: A1/D10 не пересматривается (кроме констант
   `RAMP_DAYS`/`RAMP_GAP_DAYS` из §4).

## 9. Граница раунда (что НЕ трогается)

- ML-ветка закрыта: `walk_forward`, ledger, `ml_score` — как есть (мониторинг).
- Гейт A1/D10 и окно тишины 14 дн не пересматриваются.
- Тоннаж/атрибуция (D11, E) — другие ветки, здесь не считаются.

## 10. Открытые вопросы (решить до реализации)

- **O1.** `RAMP_DAYS = 5` — или привязать к числу дней эпизода (длинная болезнь
  → длиннее рампа)? Пререгистрирую **фиксированные 5** как основной вариант;
  вариант «по длительности эпизода» — только если тесты покажут, что фикс. 5
  ломает краевой случай «две болезни подряд».
- **O2.** Целевой вес: если 1RM до болезни **выше** доступного стека — брать
  ближайший **ниже** (безопасность рампы) или ближайший вообще? Пререгистрирую
  **ниже** (рампа — осторожность).
- **O3.** Показывать ли «день рампы k из 5» явно в дайджесте или только «рампа».
  Пререгистрирую **явно** (k из N) — это и есть смысл состояния.

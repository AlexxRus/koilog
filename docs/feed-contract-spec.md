# W7 — «контракт фида источника» (пререгистрация)

**Дата:** 2026-10-22 · **Статус:** пререг; код не начат (ждёт приёмки) ·
**Основание:** пост-мортем инцидента с журналом (`BB-round6.md` §10, вне git),
решение владельца от 2026-10-22.

Документ append-only: уточнения — датированными блоками в конце, не правкой
прежних решений.

---

## 0. Что доказывает инцидент

1. `etl.load_all` (1067–1136) при переданном фиде делает
   `DELETE FROM sets WHERE source = ?` (1114 журнал, 1121 отчёт) и грузит файл
   заново. Перезапись источника **безусловна**.
2. `health/refresh._load_journal` (119–159) идёт тем же путём
   (`load_all(conn, journal=path, report=None)`) — это боевой конвейер.
3. Гардинов нет: ни проверки полноты, ни проверки формы (кроме первых четырёх
   колонок заголовка), ни снимка перед `DELETE`.
4. Живая БД уцелела **случайно**: усечённый файл грузился только в временную
   БД тестов, а боевой `load` случился уже после возврата полного файла.

**Вывод:** причинная цепь («усечённый фид молча стирает историю») закрывается
ветками (a) и (c) при действующей политике полных экспортов.

---

## 1. Политика контракта (фиксируется здесь)

| Решение | Значение |
|---|---|
| Фид источника | **полный экспорт** (вся история источника в одном файле) |
| Rolling-фид | **вне W7** → W8-кандидат (см. §5) |
| Инвариант полноты | фид может только **расти**: `n_new ≥ n_old`, `min_new ≤ min_old`, `max_new ≥ max_old` |
| Порядок обработки | разбор → **форма (warn)** → **полнота (abort)** → **снимок** → `DELETE` → вставка |
| Нарушение полноты | **громкий abort** до `DELETE`, код выхода ≠ 0, имя источника в тексте |
| Нарушение формы | **warn** (не меняет семантику загрузки) |
| Обход | явный флаг `--allow-shrink` (см. §7, развилка 1) |

Порядок обработки — часть контракта: `DELETE` не выполняется, пока не пройдены
форма и полнота, и пока не снят снимок.

## 2. Решения по веткам

### 2.1. (a) Гард полноты — abort

**Механизм.** До `DELETE` читается текущее состояние источника:
`SELECT COUNT(*), MIN(date), MAX(date) FROM sets WHERE source = ?`. Фид
разбирается в память (как сейчас — `list(load_journal(...))`), считается
`(n_new, min_new, max_new)`. Нарушением считается любое из:

- `n_new < n_old` — строк стало меньше;
- `max_new < max_old` — хвост истории отъехал назад;
- `min_new > min_old` — начало истории отъехало вперёд.

Срабатывание → `FeedShrinkError(RuntimeError)` с числами (было/стало) и
подсказкой про `--allow-shrink`. Пустая база (первая загрузка) — гард не
работает. `--allow-shrink` печатает причину и грузит.

**Точки:** `koilog/etl.py` — `load_all` (перед 1114/1121), новый
`_guard_completeness(conn, source, rows, allow_shrink)`; CLI
`koilog/cli.py` — `load`/`refresh` получают `--allow-shrink`.

**Тесты:** усечение по хвосту · усечение по началу · рост проходит ·
первая загрузка проходит · `--allow-shrink` проходит с предупреждением ·
**живая БД бит-в-бит неизменна после abort** (снимок таблицы до/после).

**Цена:** ~0.75 ч, ~60–70 строк.

### 2.2. (c) Автоснимок перед `DELETE`

**Механизм.** Таблица `sets_snapshot(id INTEGER PK AUTOINCREMENT, source TEXT
NOT NULL, taken_at TEXT NOT NULL, n_rows INTEGER NOT NULL, payload TEXT NOT
NULL)`; `payload` — JSON-массив строк источника. Снимается **после** гардов,
**до** `DELETE`. Хранится **K = 3** последних снимка на источник (старые
удаляются тем же вызовом). Откат — `restore_source(conn, source, snapshot_id)`
(пишет строки обратно в `sets` через тот же `upsert`, затем
`recompute_metrics`).

**Точки:** `koilog/etl.py` — `_SCHEMA` (+таблица), `snapshot_source`,
`restore_source`; CLI — `load --restore SNAPSHOT_ID` (или `snapshot --restore`,
развилка 2).

**Тесты:** снимок снимается до удаления · retention K=3 · откат возвращает
бит-в-бит (сверка `as_tuple()` всех строк) · откат на пустой БД.

**Цена:** ~1.25 ч, ~80 строк. Диск: ~4 МБ на снимок журнала (15461 строка),
K=3 → ~12 МБ на источник.

### 2.3. (d) Форма фида — warn (отдельная ветка)

**Механизм.** `check_feed(path, source) -> FeedShape` с полями
`header_ok`, `header_variant`, `n_records`, `blank_records`, `monotonic`,
`inversions`, `bad_dates`, `note_only_rows`, `warnings: list[str]`.
Вызывается из `load_all` после `_require_file`, до гарда полноты.

| Чек | Что значит | Политика |
|---|---|---|
| Заголовок: первые 4 колонки = `ДАТА;ВРЕМЯ;ТРЕНИРОВКА;УПРАЖНЕНИЕ` | структурная возможность разбора | **abort** (уже есть, 820–825) |
| Заголовок: полный набор колонок отличается от канонического | вариант экспорта (в `broken-reversed`: `ВЕС КГ`, `ВРЕМЯ С`) | **warn** |
| Монотонность дат (неубывание) | обратный порядок = источник инверсии `source_row` | **warn** |
| Плотность пустых записей > 1% | 1553/17014 = 9.1% в `broken-reversed` | **warn** |
| Записи без даты | нечитаемые строки | **warn** (с числом) |
| Note-строки с эмодзи (`;;;;;;;;"🙂"`) | штатные заметки, 10 шт. | **info** (не warn) |

**Точки:** `koilog/etl.py` — `check_feed`, `FeedShape`; `LoadReport` получает
`warnings: list[str]`; CLI печатает их в stderr, `refresh` — строкой
«внимание: ...» в стадии журнала.

**Тесты:** реверс → warn · пустые разделители → warn · вариант заголовка →
warn · нет заголовка → abort · note-строки → info без warn · чистый фид → нет
warnings.

**Цена:** ~1.0 ч, ~50–60 строк + 6 тестов.

### 2.4. (e) Семантика `source_row` — docs + пин-тест

**Определение (фиксируется).** `source_row` = порядковый номер **CSV-записи**
в файле, 1-based, **заголовок не считается**, **пустые записи считаются**
(`load_journal`: `enumerate(reader, start=1)`, пустая запись — `continue` без
уменьшения счётчика). Поэтому в файле с пустыми разделителями номера
«съедаются»: 15461 запись + 1553 пустые = max `source_row` 17014.

**Что правится:** docstring модуля `koilog/etl.py` (строки 19–22) утверждает
«новую выгрузку можно добавить к истории, не перезаписывая её целиком» — это
противоречит `load_all` (полная замена источника). Docstring переписывается
под фактическое поведение: ключ идемпотентен, но политика — **замена
источника целиком**; «добавление к истории» = передача более полного файла.

**Пин-тест:** на синтетике (заголовок + 2 записи + 3 пустые + 1 запись) —
`source_row` = `[1, 2, 6]`, max = 6; на каноническом журнале — max = 15461.

**Цена:** ~0.25 ч (docs + 2 теста).

### 2.5. (f) Негативные фикстуры — синтетика в git

В git кладётся **синтетика** (мелкая, shape-эквивалентная); реальный
`data/journal.csv.broken-reversed-20261022` (1.44 МБ) остаётся **вне git** как
улика (реестр §10.5).

| Класс аномалии | Файл (в `tests/fixtures/feeds/`) | Ожидание |
|---|---|---|
| чистая минимальная синтетика | `journal_ok.csv` | грузится молча |
| **обратный порядок дат** | `journal_reversed.csv` | warn |
| **пустые разделители** | `journal_blanks.csv` | warn (> 1%) |
| **note-строки с эмодзи** | `journal_notes.csv` | info, не warn |
| **вариант без заголовка** | `journal_no_header.csv` | abort |
| **вариант заголовка** | `journal_header_variant.csv` | warn |
| **усечённый фид** (только последние 2 дня) | `journal_truncated.csv` | abort полноты |

Синтетика обязана воспроизводить **все** классы `broken-reversed`, а не только
реверс (решение владельца).

**Цена:** ~0.75 ч.

### 2.6. (g) Live-data тир — свойства вместо констант

`tests/test_etl.py`: числа R-1a (`15451`, `945`, `20995`, `1399`, `2045`)
заменяются **производными идентичностями** и полом:

- `last_day` = `max(date)` по файлу; `days` = `len(distinct date)`;
  `sessions` = `len(distinct session_id)` — считаются из тех же данных, не
  хардкодятся;
- `report.journal == len(rows)`; `report.total == report.journal + report.report`;
- `report.journal > 15_000` (пол — защита от усечения фида в тесте);
- `first_day == "2015-06-21"` остаётся (историческая константа отчёта);
- 11 общих дат остаются (стык с замороженным `report.csv`);
- `test_export`: `written == total`.

Комментарии R-1a «as-of 2026-10-22, заменяется live-data тиром (W7)» —
**снимаются** (тир наступил).

**Цена:** ~1.0 ч, ~8 ассертов.

## 4. Критерии выхода (приёмка)

1. **Негативный тест усечения**: усечённый фид → громкий abort **до**
   `DELETE`; живая БД **бит-в-бит неизменна** (сверка снимка `sets` до/после).
2. **Тесты формы**: реверс, пустые разделители, note-строки с эмодзи, вариант
   без заголовка, вариант заголовка.
3. **Тест отката снапшота**: снимок → испорченная загрузка → `restore_source`
   возвращает бит-в-бит.
4. **Пин-тест `source_row`** (§2.4).
5. **Live-data тир зелёный**, «as-of»-констант нет.
6. `python -m unittest discover -s tests` → `OK (skipped=1)` **с явной дельтой
   `Ran`** относительно 759 (сколько добавлено — назвать числом).

## 7. Открытые развилки (нужны к приёмке пререга)

1. **Имя флага обхода.** `--allow-shrink` (предложение) против
   `--replace-feed` / `--force-feed`. Смысл: «я знаю, что фид короче, грузи».
2. **Где хранить снапшоты.** Таблица `sets_snapshot` в `sql/training.db`
   (предложение; откат одним SQL) против файлов в `data/snapshots/`.
   Retention K=3 — согласовать.
3. **CLI отката.** `load --restore ID` (предложение) против отдельной команды
   `snapshot --restore`.
4. **Строгость заголовка.** Сравнивать полный набор колонок (warn при
   отличии) или оставить первые четыре (сейчас) и только логировать.
5. **Порог плотности пустых записей.** 1% (предложение) — канон 0%,
   улика 9.1%; порог 1% даёт запас.

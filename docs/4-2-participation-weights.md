**Статус:** закрыт (датированная нота 2026-10-23). **Решение:** веса участия **не вводить** в рамках 4.2. **Фенс:** кросс-режимные/кросс-метричные сравнения **только по явному новому пререгу**, пред-авторизованных обходов нет; веса **никогда** не должны протекать в `state`, `retrain`, `gate`, `ramp`, `digest.recommend`, `ml_features`, `ml_labels`. **4.2 ≠ W5–W6**: при будущем вводе обязательны нормировка `sum=1.0`, робастность **±20%** (переворот пары A>B→B>A при возмущении с пере-нормировкой → не вводить), проверка таблицей top-N/пар по всем весам по ±20% (**гиперкуб 2^n**, при n>10 **Монте-Карло ≥10k**), «переживает» = **качественный** вывод тот же. ## 1. Проблема: «вес участия» vs «нагрузка группы»

У составного движения (напр. жим лёжа затрагивает трицепс, приседания — кор) есть **две разные** величины:
1. **Нагрузка самой группы** (тоннаж/подходы/время по её упражнениям) — уже есть в `health/groups.py` по (группа × режим). Единица измерения разная между режимами.
2. **Участие в движении** (доля группы в нагрузке другого движения) — **веса участия**.

**Ключевой принцип:** нельзя «взвесить» тоннаж (кг) и подходы (штуки) и секунды в одну сумму. `groups.py` уже структурно запретил кросс-режимную сумму внутри группы (§2.5). Любые веса участия **должны** уважать ту же границу: либо **внутри одной метрики/ветки**, либо требовать **отдельного пререга** (кросс-метричный).

Также 4.3 явно не вводил взвешивания (простое среднее) — см. §11 пререга 4.3.

## 2. Замер премисы (read-only)

### 2.1. Состав групп/режимов
См. выше: 3 смешанные группы, 17 однорежимных. Ключ (группа × режим) покрывает разбиение без правки `exercise_group` в `sets` (B в §2.5 E отклонён осознанно).

### 2.2. Возможные применения весов участия
Возможные кандидаты (требуют пререгистрации, если реализуются):
- **Внутри железной ветки**: при сумме «косвенной» нагрузки железных групп — только если все слагаемые в **одной метрике** (тоннаж) и определены явно.
- **Мышечная карта** (анатомическая): доли для анализирующей сводки — **справочная**, не должна влиять на `state/gate/ramp/recommend`, на `ml_features`, на решения.
- **Сопоставление балансов**: `balance` уже сравнивает **две группы одной ветки/метрики**; веса участия в формулу баланса вводить нельзя без пререга.

**Пока нет** однозначного запроса, который бы требовал **обязательных** весов для существующего кода. Замер показывает, что структура (группа × режим) уже есть.

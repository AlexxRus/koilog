## §4 Развилка F-1: считать ли разминку в `load_daily.sets`

`load_daily.sets` = `COUNT(*)` без фильтра разминки (окно
2024-01-16 … 2026-10-27, 1 016 дней, сумма **6 281**). Разминочных строк в
окне — **658**.

- **A (рекомендуется): колонку не трогать.** `sets` остаётся «числом строк дня»
  (модельная величина: на ней висит суррогатный sRPE — `sets * 3.5 мин`, когда
  нет часов). Витрина показывает рабочие подходы отдельно (§5), числа сходятся.
  Тоннаж/`tonnage_iw`/`koi_sum` не меняются вовсе: у разминки `weight`/`koi`
  NULL. Замер на копии с поднятым флагом: `_session_rows` — 0 различающихся дней
  из 1 403, `load_daily` совпадает поточечно; `acwr`/`monotony`/`rm_regress`
  те же.
- **B (отклоняется):** `COUNT(*) FILTER (is_warmup = 0)`. Цена: `sets` 6 281 →
  5 623, и на **4 днях** окна суррогатный sRPE считается от `sets` (нет силовой
  тренировки в часах) → меняется `srpe` → `acute`/`chronic`/`acwr`/`ewma` →
  `ml_features` → **ledger `ml_score`**. Это прямая запись в guarded-поверхность
  и нарушение авто-стопа §9. Плюс разъезжается смысл колонки («строки дня» vs
  «рабочие подходы»).

**Решение владельца: A.** Колонка `load_daily.sets` остаётся «числом строк
дня» (6 281 в окне, из них 658 разминочных); рабочие подходы показывает витрина
(§5, ключ `sets_working`). Прогноз Task 106 («−660 в `load_daily.sets`»)
владельцем **отозван** (журнал, Task 124): при варианте B −658 ушло бы в
`ml_features` через суррогатный sRPE четырёх дней, то есть в guarded-поверхность
и в ledger. Сдвиг −658 живёт на уровне витрин и сходится строкой K-2 (§5).

## §5 Поверхность опции и рендер

**Опция.** Одно имя на всех уровнях: `include_warmup: bool = False`.

1. `stats.exercise_report(conn, *, ..., include_warmup: bool = False)` —
   фильтр `AND is_warmup = 0` в `_TOTALS_SQL` (в `_BEST_LAST_SQL` не нужен:
   там `rm IS NOT NULL`, а у разминки `rm` NULL во всех 827 — закреплено
   тестом).
2. `health.load.summarize(conn, *, include_warmup: bool = False)` и
   `format_summary(conn, *, include_warmup: bool = False)`. Ключи сводки:
   `sets` (колонка `load_daily`, модельная, **6 281**), `warmup` (658),
   `sets_working` (5 623).
3. CLI: `stats --include-warmup`, `health-load --include-warmup` (симметрия с
   ноутбуками; дефолт — выключено).
4. Ноутбуки: `koiLog.ipynb` ячейка 3 (сводка упражнений) и
   `koiLog-health.ipynb` ячейка 3 (сводка нагрузки) получают в начале ячейки
   `УЧИТЫВАТЬ_РАЗМИНКУ = False` и передают его параметром.
5. `stats.window_sets(conn, since=None)` — счётчик окна `(всего, рабочих)` для
   строки K-2; отдельная функция, потому что таблица ячейки 3 фильтрует по 1RM
   и разминочной строки в ней нет ни в одном положении переключателя.
6. Внутренний `_one_stats` (программа, план, `explain`) зовёт сводку с
   `include_warmup=True`: это разбор одного имени, а не витрина, поэтому
   поведение для «Разминки» остаётся прежним, а для настоящих упражнений
   фильтр не меняет ничего (другое имя).

**Рендер сводки нагрузки — в обоих положениях** (развилка F-3 / S-1):

- `include_warmup=True` — **байт-в-байт как сегодня**:
  `подходов: 6281   тоннаж: 1262745 кг`.
- `include_warmup=False` (дефолт):
  `подходов: 5623   тоннаж: 1262745 кг` + отдельная строка
  `  разминка: 658 подходов не входит в счётчик`.

Тоннаж в строке — **один и тот же** в обоих положениях (1 262 745 кг):
разминка в него не входит ни сейчас, ни потом (вес NULL). Ни порогов, ни
стрелок, ни оценок в рендере не добавляется.

**Что опция НЕ покрывает (и почему):**

- карточка дня (`digest`) — guarded, параметра не получает; сдвиг её строки
  «кардио» идёт через `groups`, которая фильтрует разминку **уже сейчас**
  (предзарегистрирован в §6, развилка F-4);
- `groups` / `muscle_load` — в ноутбуках не вызываются (ячейки 13/14 зовут
  `muscle_load`, он иммунен), это слои нагрузки/витрин со своим фильтром;
- `recent_exercises` (ячейка 7) — список реально введённых имён; прятать
  введённое имя из него нельзя;
- `explain` (ячейка 9) — разбор одного упражнения; разминка — другое имя,
  поэтому в разборе «Жим гантелей» её нет ни до, ни после. Метка `разм`
  проверяется CLI-прогоном (§10).

**Развилка F-2: где переключатель в koiLog.** Ячейка 3 зовёт сводку с
`with_rm_only=True`, а у разминки 1RM нет → **в таблице ячейки 3 разминки нет
ни в одном положении переключателя** (замер: 11 строк, 473 подхода, одинаково).
- **K-1 (рекомендуется):** переключатель стоит в ячейке 3, честно
  задокументирован; его видимый эффект — CLI (`stats` без `--rm-only`) и
  `--all`.
- **K-2 (принято):** плюс печатать в ячейке 3 строку «подходов в окне: N (без разминки:
  M)» — переключатель становится видимым в ноутбуке; цена: новая строка
  рендера и второй запрос/агрегат в ячейке. Реализация — `stats.window_sets`
  (то же окно, что у сводки: `skipped = 0`, `is_outlier = 0`, `date >= since`);
  скобка **зеркалит** положение переключателя: выключен — `586 (с разминкой:
  641)`, включён — `641 (без разминки: 586)`. Так строка не врёт ни в одном
  положении и не вводит второе число без подписи.

## §12 Операционный шаг: журнал сам не перезагрузится

`is_warmup` считается при разборе файла. `refresh` пропускает неизменённый
журнал по слепку `mtime:size` (`refresh.py:104-113`, `JOURNAL_KEY`) — значит
после обновления кода **без** правки `journal.csv` база останется с
`is_warmup = 0`, и фикс «молча не сработает». Два выхода:

- разово выполнить `python -m koilog load` (полная перезагрузка фида; W7:
  снимок снимается до `DELETE`, файл не усох — отказ не срабатывает);
- либо дождаться следующей записи в журнал — её `mtime`/размер изменится, и
  `refresh` переразберёт файл целиком.

В этом пререге рекомендуется **O-1**: шаг входит в §10 и в README (одна
строка «после обновления — `load`»). Автосброс кэша по версии правил (O-2) —
отдельный пререг: он трогает `refresh.py` и слепки, то есть конвейер, а не эту
задачу.

## 3. Механизм (закрывает оба остатка)

**921 ↔ 931 — не разная коллекция.** Коллекция в обоих деревьях ровно **931**
(замер `TestLoader` + поштучный дифф id: 0 в обе стороны). `Ran` — это
`testsRun`, то есть **стартовавшие** тесты, а `SkipTest` из `setUpClass`
не стартует ни одного метода класса: 931 − 7 − 3 = **921**. В E1 скип только
у одного класса, второй падает в `setUpClass`, поэтому 931 − 3 = **928**.

**34 / 35 / 36 — три состояния схемы, а не три разных окружения.**

- **34** = скипы, не связанные с БД: 20 «нет `data/journal.csv` и/или
  `data/report.csv`» + 11 «нет `data/journal.csv`» + 2 «нет `data/report.csv`»
  + 1 «sklearn есть: подсказка про extra ml не проверится».
- **36** = те же 34 + два классовых скипа (класса нет в дереве без БД).
- **35** = 34 + один **внутритестовый** скип `test_orphan_days_are_episode_tails`
  («в живой базе нет дней без канона») — он срабатывает, когда `ml_score` есть,
  но пуст (E3), и класс успевает стартовать.

## 4. Дефект

Гвард обоих классов — `Path.exists()`. Файл БД, оставшийся от `load` в пустом
дереве (E2), от `score` на пустой базе (E3) или просто нулевой файл (E1),
проходит гвард, и класс падает: 7 не-прохождений в E2, 7 в E1, 3 в E3 — с
именами, указывающими на данные, хотя данные тут не при чём. Это же и есть
причина, по которой канонический отпечаток приёмки зависит от состояния БД
(лид зафиксировал это в 4-15).

## 5. Гвард-предикаты (решение)

**A. `RealProgramInventoryTests`** (`tests/test_stats.py`): файл есть **и**
таблица `sets` есть **и** `COUNT(*) FROM sets > 0`. Иначе `SkipTest`:

- нет файла → «нет базы <path>: выполните load»;
- таблицы нет (E1) → «в базе <path> нет таблицы sets: выполните load»;
- таблица пуста (E2/E3) → «база <path> пуста: в sets нет подходов — выполните load».

**B. `LiveCanonTests`** (`tests/test_health_canon.py`): файл есть **и** таблица
`ml_score` есть **и** `COUNT(*) FROM ml_score > 0`. Иначе `SkipTest`:

- нет файла → «нет живой базы: <path>» (текст сохраняется — он же в E0);
- таблицы нет (E1, E2, E4) → «в базе нет таблицы ml_score: выполните
  refresh --deep (или score --replay)»;
- таблица пуста (E3) → «ledger ml_score пуст: выполните score --replay».

**`ml_features` отдельно не проверяется.** Непустой `ml_score` означает, что
`score._ready` (`score.py:151`) уже требовал `ml_features` + `ml_labels`:
строки ledger'а без них не появляются. Отдельная проверка была бы дублем
инварианта, который держит код.

**Форма реализации.** По локальному приватному хелперу в каждом файле
(8–12 строк: `sqlite_master` + `COUNT(*)`, соединение `mode=ro`), без нового
общего модуля: `tests/` не имеет `__init__.py` и support-модуля, заводить его
ради двух вызовов — лишняя поверхность (развилка F1).

## 6. Чего гвард НЕ прячет (граница — главное в этом юните)

- **Не** проверяется «есть ли строки под **текущей** спекой». Это утверждение
  самих тестов (`test_canonical_series_has_single_spec`,
  `test_repeat_scoring_does_not_change_the_day_frame`). Ledger, заполненный
  только винтажом, обязан **падать** — иначе починенный гвард замаскировал бы
  ровно тот дефект, ради которого тесты написаны (развилка F2).
- **Не** проверяется «есть ли упражнения с 1RM» в A — это предмет
  `test_there_are_exercises_to_check`.
- Пустая `sets` при непустом ledger'е → A скипается, B работает: поверхности
  разные, один гвард не подменяет другой.

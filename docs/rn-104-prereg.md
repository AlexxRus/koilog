## §1 Объём и границы

**Что закрываем:** витринную отметку «какая нагрузка была перед пропуском длиннее двух
недель». Это **display-only** слой: чтение уже посчитанных нагрузок и календаря.

**Что НЕ делаем:**
- не пишем в базу (`sets`, `load_daily`, `ml_*` не трогаются);
- не меняем правила гейта/рампы/состояния (`state.py`, `retrain.baseline_gate`);
- не вводим ни одного нового порога «критичности» без замера (§2.6 показывает, что
  односторонний порог «высокая нагрузка» ловит меньшинство своих же пропусков);
- не трогаем семантику E после RM-98 (`weight` уже хранит E для `vest_only`) и
  лестницу R5B.

**Границы скрытой сложности (измерено, §2):**
- готовый детектор простоя уже есть (`load.gap_runs`, `load.ACWR_GAP_DAYS = 14`),
  но `load_daily` живёт с `DEFAULT_WINDOW = "2024-01-16"` — на дефолтном окне
  пропусков **4**, на полной истории — **27**. Если читать только `load_daily`,
  отметка молча соврёт «за 11 лет было 4 пропуска»;
- `return` уже показывает **простои по упражнению** и детрейн-кривую; пропуск
  упражнения ≠ пропуск тренировок (смена программы). Смешивать нельзя.

из них «свои» (is_foreign = 0): 1 400 дат

### 2.3 Определение «пропуска»: свип по датам севов (`is_foreign = 0`)
```
разница между соседними датами > 14 дн: 27 пропусков
                              > 15 дн: 26
                              > 17 дн: 21
                              > 21 дн: 15
```
Строгое чтение README «**больше** двух недель» = простой **> 14 дней** (15+ дней без
тренировки) → **26**; вариант «≥ 14 дней» добавляет ровно один случай — простой
ровно 14 дней (2017-12-20 … 2018-01-02).

Тот же счёт через готовый детектор на непрерывном дневном ряду
(`load.gap_runs(tonnage, gap)` — простой = подряд идущие дни с нулевой нагрузкой):
```
полная история (4 147 дней): gap=14 → 27 прогонов
                             длины: 16,38,20,16,24,14,30,16,16,20,81,44,38,20,265,
                                    18,45,46,27,26,57,34,22,20,19,16,30
дефолтное окно load_daily (1 016 дней): gap=14 → 4 прогона
                             2024-07-12…07-31 (20 дн), 2025-08-06…08-24 (19),
                             2025-12-27…2026-01-11 (16), 2026-02-10…03-11 (30)
```
**Границы по датам севов:** прогон = (первый нулевой день, последний нулевой день);
возврат — первый день с нагрузкой после прогона. Совпадает с семантикой `gap_runs`.

### 2.4 `is_foreign = 1`: вклад в «нагрузку перед пропуском»
```
полная история, чужие включены: 27 пропусков, медиана T14 = 16 621
полная история, чужие исключены: 27 пропусков, медиана T14 = 16 621
```
**Ноль влияния.** 63 чужие строки лежат на трёх датах 2021-08/09, ни одна не является
границей пропуска и не попадает в 14-дневные окна «перед пропуском» (сдвиг был бы
виден как разница медиан — её нет). Это согласуется с фенсом D3/D4: health-модули
`is_foreign` не знают; `load._session_rows` фильтрует только `is_outlier`.

### 2.5 «Нагрузка перед пропуском»: распределение (полная история)
Метрика — тоннаж `load._session_rows` (исключены выбросы; из тоннажа исключены
разминка, `skipped`, гравитрон; `weight` для `vest_only` уже E по RM-98).
```
предпропускной T14 (n = 27): min 3 588 · медиана 16 621 · max 60 411
дней с нагрузкой в окне 7 дн / 14 дн перед пропуском: 1…5 / 2…10
все дни, скользящее 14-дневное окно: медиана 16 380 · p75 26 714 · p90 35 121
предпропускной T14 в перцентилях собственной истории: 3/27 ≤ p25 · 7/27 ≥ p75
                                                      → 17/27 в средней половине
```
**Вывод замера:** «нагрузка перед пропуском» **не** систематически высокая: только
7 из 27 пропусков (26 %) шли после нагрузки верхнего квартиля; 3 из 27 — после
нагрузки нижнего; большинство — обычная середина. Односторонний ярлык «критическая
нагрузка» описал бы меньшинство собственных пропусков.

| Вариант | Описание | Цена/риск | Замер |

### Р3 — Метрика «нагрузки перед пропуском»

| Вариант | Описание | Замер/цена |
|---|---|---|
| **A** (рекомендуется) | тоннаж (E-объём) за 7 и 14 дней до первого нулевого дня + число дней с нагрузкой | готовый канон `_session_rows`; `weight` = E по RM-98 автоматически |
| B | e1RM-тренд до/после | уже есть: `retrain.detraining_curve` (и `returns` печатает) — дубль |
| C | только число подходов | теряет величину нагрузки (10 подходов лёгких ≠ 10 тяжёлых) |

**Рекомендация: A.** Оба окна (7 и 14) показывать рядом: они отвечают на разные
вопросы («свежая» и «накопленная» нагрузка), и это не два порога, а два числа.

### Р4 — Порог «критической»

| Вариант | Описание | Замер |
|---|---|---|
| A | фиксированный порог тоннажа | нет обоснования числа; история разъезжается на порядок (3 588…60 411) |
| B | перцентиль собственной истории | перцентили предпропускных: 19.5 %…99.7 %; порог «≥p75» ловит 7/27, «≤p25» — 3/27 |
| **C** (рекомендуется) | **без ярлыка**: показывать число и перцентиль, не навешивать «критическая» | §2.5: высокая нагрузка предшествует лишь 26 % пропусков — ярлык описывает меньшинство |
| D | порог + честный отказ на тонкой истории | дороже, а ярлык всё равно не подтверждён замером |

**Рекомендация: C** + обязательное правило тонкой истории: если у ряда меньше
`MIN_GAPS = 3` завершённых пропусков, перцентиль **не печатать** (честное
«недостаточно истории для перцентиля», паттерн GP-139/п. 5). Число тоннажа печатается
всегда — оно не требует истории.

### Р5 — Формат отметки

| Вариант | Описание |
|---|---|
| **A** (рекомендуется) | строка в `digest`: `перед пропуском 2026-02-10…03-11 (30 дн): объём 7 дн — 2 208 кг, 14 дн — 12 606 кг; дней с нагрузкой 1/6` + при накопленной истории `(31-й перцентиль)` |
| B | колонка `return` | отклонено Р1 |
| C | отдельная команда | отклонено Р1 |

**Поведение без пропусков (пин):** если до запрошенного дня завершённых пропусков
`> 14` дней нет — строка **есть**, но честная: «пропусков больше двух недель не было»,
а не молчание (паттерн «честная пустая схема», GP-139). Если пропуск ещё **не
завершён** (сегодня внутри простоя) — показывать «идёт простой, N дней (с DATE)»,
но не выдавать его за завершённый.

## §5 Пины (должны остаться зелёными после фикса)

1. **База без пропусков:** `digest` на синтетике без пропусков печатает остальные
   строки байт-в-байт как до фикса; новая строка — только «пропусков больше двух
   недель не было».
2. **Граница «ровно 14 дней»** (2017-12-20…2018-01-02): при `gap=15` — **не** пропуск;
   живой тест-свойство на полной истории: 26, не 27.
3. **Окно истории:** отметка видит 2015–2023 (полная история), а не только `load_daily`
   (пин: первый пропуск 2015-08-13…2015-08-28 присутствует в выдаче).
4. **E-семантика RM-98 / R5B:** `sets.weight` не пересчитывается, `available_weights`
   не трогается; `etl.py` дифф 0 B.
5. **`return` не меняется:** вывод `return` на тех же данных идентичен (пин на
   отсутствие диффа в `cmd_return`/`retrain`).
6. **Ноутбуки** не трогаются (0 B).
7. **Пустая база:** `digest` без данных по-прежнему отказывает кодом 1 (GP-139), новая
   строка не рисуется на пустоте.

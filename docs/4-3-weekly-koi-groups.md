# 4.3 — недельный КОИ по группам мышц: пререгистрация

**Статус:** пререг, кода нет. Развилки закрывает владелец **до** кода.
**Заказ:** round6 §4.3 (round5 §9.4): агрегация КОИ по мышечной группе за
неделю, CLI `weeks --group`, пересчёт полос `core.KOI_BANDS_WEEK` под выросшие
суммы, нормализация push-up/pull-up.

Документ фиксирует **проверку премисы заказа замером** и три развилки с ценами
и рисками. Решения — в §8.

## 0. Что уже есть (и что нельзя дублировать)

| Место | Что умеет | Что это значит для 4.3 |
|---|---|---|
| `etl.SESSION_KOI_VIEW` / `WEEKLY_KOI_VIEW` | `koi = reps / ((1 − weight/rm_ma_30d) · 100)`, cap `w ≤ 0.98·RM`, суммы по упражнению за вечер и за неделю, полосы дня `KOI_BANDS` и недели `KOI_BANDS_WEEK` | КОИ считается **по упражнению**; `v_weekly_koi` = 4036 строк (неделя × упражнение) |
| `core.KOI_BANDS_WEEK` | `2.0 → Лёгкий`, `3.0 → Тяжёлый`, `4.0 → Очень тяжёлый`, иначе «Вы сошли с ума??» | пороги **абсолютные**, заданы для суммы одного упражнения |
| `stats.weekly_koi(..., group=...)` | фильтр по `exercise_group` **уже есть** | пункт «CLI `weeks --group`» из плана **частично закрыт**: флаг есть (`cli.py:1096`), но это фильтр по-упражненных строк, **не** агрегат |
| `health/groups.py` (`aggregate`, `series`, `series_by_mode`, `balance`) | погрупповая **нагрузка**: тоннаж/подходы/время по `taxonomy.group_of` × режим, недельное скользящее окно | объём группы **уже виден**; 4.3 не должно повторять тоннаж |
| `taxonomy.GROUPS` (20 групп), `taxonomy.group_of`, `NO_RM_GROUPS`, `WEIGHT_MODE_OVERRIDE` | ключ группы — таксономия, не эвристика по названию (D11) | группу берём из `exercise_group`; весов участия **нет** (это 4.2) |

Три следствия, которые нельзя обойти:

1. **КОИ определён только там, где есть база 1RM.** `NO_RM_GROUPS = ('ПРЕСС',
   'ПОДЪЁМ НОГ', 'ПЛАНКА', 'КАРДИО')` — эти группы в `v_weekly_koi`
   **отсутствуют структурно** (16 групп из 20 в данных). Витрина «КОИ по всем
   группам мышц» физически неполна, и это надо писать, а не замалчивать.
2. **КОИ — интенсивность, а не объём.** Тоннаж группы уже есть в
   `health/groups.py`; складывать КОИ разных упражнений в «объём группы» —
   смена смысла, а не агрегация.
3. **Докстринг `stats.weekly_koi` прямо запрещает складывать** («у каждого
   упражнения своя база 1RM, поэтому складывать жим и тягу в одну сумму
   нельзя»). Развилка 0 — не формальность: план 4.3 противоречит записанному
   решению, и это надо решать явно, а не молча.

## 1. Проверка премисы заказа: три утверждения против замера

Замеры — по живой базе, только чтение (SQL в §9). Числа — на 2026-10-22.

### 1.1. «Отжимания/подтягивания живут на своём весе и входят в групповой КОИ в несопоставимом масштабе» — **опровергнуто**

КОИ — отношение (`weight / rm_ma_30d`), поэтому масштаб веса **сокращается**:

| режим | подходов с базой 1RM | КОИ подхода, медиана | `w/RM`, медиана | доля `w/RM > 0.98` (cap) |
|---|---|---|---|---|
| `absolute` (железо) | 14 833 | **0.34** | 0.74 | 2.5 % |
| `total_bodyweight` (подтягивания, брусья) | 1 648 | **0.36** | 0.78 | 0.2 % |
| `vest_only` (отжимания, пресс) | 243 | **0.41** | 0.82 | 0.0 % |

Недельные суммы по упражнению — тот же масштаб:

| класс | строк (неделя × упражнение) | медиана `koi_week` | q25 | q75 | q90 | max |
|---|---|---|---|---|---|---|
| своё тело | 468 | **1.20** | 0.85 | 1.55 | 2.25 | 8.15 |
| железо | 3 568 | **1.21** | 0.98 | 1.53 | 2.26 | 11.40 |

Разница медиан — **0.01**. Отдельные упражнения (среднее `koi_week`):
Подтягивания 1.44 (242 недели), Отжимания на брусьях 1.63 (76), Брусья 1.36
(52), Отжимания 1.08 (88) — все четыре лежат **внутри** железного диапазона
средних (0.38–2.59 по 91 упражнению, медиана средних 1.17). Подтягивания и
брусья выше медианы, отжимания ниже.

**Вывод:** нормализация «своего тела» по масштабу не нужна — масштаб уже
общий. (Историческая причина «все суммы в „сошли с ума“» — отсутствие `/100`
в формуле — устранена; см. комментарий в `etl.py` перед `_KOI_UPDATE`.)

### 1.2. Настоящая асимметрия — не масштаб, а **отсутствие** КОИ

`vest_only`: 1 552 подхода без skip/timed, из них **1 309 (84.3 %) без КОИ**.
Непересекающееся разложение (сумма = 1 309; важная деталь — `rm_ma_30d` живёт
на **упражнении**, а не на строке, поэтому «вес NULL» и «1RM есть» не
исключают друг друга, и считать надо аккуратно):

| причина | подходов | почему |
|---|---|---|
| дизайн таксономии: `NO_RM_GROUPS` | **1 143** | пресс/планка/подъёмы ног не считают 1RM **намеренно** (`Скручивания` 662, `Подъем ног в висе` 362, `Скручивания лежа` 90, `Приседания` 32…) |
| нулевая добавка → `weight = None` | **146** | `etl.resolve_bodyweight` возвращает `None` при нулевой добавке; в основном `Отжимания` 109 |
| вес есть, 1RM ещё не накоплен | **20** | окно 30 дней не заполнено (`Отжимания` 40 в сырых строках, 20 после skip/timed) |
| всё есть, но cap `w > 0.98·RM` | **0** | у `vest_only` cap **не срабатывает ни разу** |

То есть 84 % — это **два записанных решения** (пресс не меряется 1RM;
нулевая добавка = нет веса), а не ошибка формулы и не cap. Там, где КОИ у
`vest_only` есть (243 подхода; у `Отжиманий` — 240 из 349 не-skip/timed,
68.8 %), он **в масштабе** (§1.1).

### 1.3. «Полосы под выросшие суммы» — суммы выросли мало, потому что группа-неделя почти всегда из одного упражнения

`SUM(koi_week)` по (неделя, группа), 3 348 строк, 16 групп:

| метрика | медиана | q75 | q90 | max | >2 | >3 | >4 |
|---|---|---|---|---|---|---|---|
| **сумма** по группе | 1.37 | 1.92 | 2.99 | 13.62 | 23.9 % | 9.9 % | **4.7 %** |
| **среднее** по группе | 1.22 | 1.53 | 2.22 | 11.40 | — | — | **1.7 %** |
| (для сравнения) по упражнению | 1.21 | 1.54 | 2.26 | 11.40 | 13.3 % | 4.6 % | **2.0 %** |
| сумма отношений к своей медиане | 1.08 | 1.65 | 2.30 | 10.92 | — | — | — |

Почему сумма почти не растёт: **81.5 %** групп-недель (2 727 из 3 348)
состоят ровно из **одного** упражнения (медиана n = 1, q90 = 2, max = 4).
`сумма − максимум` по группе-неделе: медиана **0.00**, q90 1.00, max 4.79.
Полосу меняет добавление второго упражнения только в **9.1 %** строк.

При этом сумма **удваивает** долю «Вы сошли с ума??»: 2.0 % → **4.7 %**
(и это ещё мягко, потому что 81.5 % строк — одиночные). Максимум суммы
13.62 = `Сгибание ног лежа` 10.94 + `Разгибания ног` 2.69 (2020-W39), то есть
тянет его **одно** упражнение, а не группа.

### 1.4. Что следует из проверки премисы

* Нормализация push-up/pull-up **не имеет предмета** (1.1); «потеря» 84 %
  подхода — дизайн (1.2), и лечить её надо **подписью**, а не пересчётом.
* Пересчёт полос нужен **только** если полоса группы считается по **сумме**;
  у 18.5 % строк есть второе упражнение (n ≥ 2), но полосу это меняет лишь в
  **9.1 %** строк, зато сумма удваивает хвост «сошли с ума» (1.3).
* Значит развилки ниже — про **выбор витрины**, а не про «доделать
  недостающее».

## 2. Развилка 0. Агрегировать ли КОИ по группе вообще?

### 0-A. Не агрегировать: оставить фильтр `weeks --group`

Что: ничего не делать; план закрыть пометкой «фильтр уже есть».
Цена: 0 кода, 0 тестов, 1 строка в карте.
Риск: «витрины по группам» нет; пользователь по-прежнему смотрит 508 строк
`ЖИМ ЛЁЖА` за все недели и складывает глазами.

### 0-B. Витрина **без суммы**: `(неделя, группа) → n, КОИ ср, КОИ макс, подходы` + полоса по **среднему** ★ рекомендация

Что: новый вид `v_weekly_koi_group` (агрегат по `week, exercise_group` из
`v_weekly_koi`), функция `stats.weekly_koi_by_group`, флаг `weeks --by-group`.
Колонки: `неделя | группа | упражнений | подходов | КОИ ср | КОИ макс | режим`.
«Режим» — существующие `KOI_BANDS_WEEK` по **среднему** (среднее живёт в том же
масштабе: медиана 1.22 против 1.21 по упражнению), поэтому новых констант нет.
Цена: 1 вид + 1 функция + 1 флаг + подпись, ~80 строк кода, ~10–14 тестов.
Риск: «среднее» отвечает на «типичная интенсивность упражнений группы», а не
«сколько группа получила за неделю» (объём — в тоннаже `health/groups.py`);
это надо написать в подписи, иначе витрину прочтут как объём.

### 0-C. Витрина **с суммой** (буквальное чтение плана) + полоса по сумме

Что: то же, но колонка `КОИ = SUM(koi_week)` и полоса по сумме (нужны новые
константы — развилка B).
Цена: 0-B + 1 константа + 1 рендер.
Риск: противоречит докстрингу `weekly_koi`; в 81.5 % строк сумма = одно
упражнение (витрина показывает то же, что по-упражненная); хвост «сошли с
ума» удваивается (2.0 % → 4.7 %); «сумма КОИ» не является объёмом, потому что
КОИ — безразмерная интенсивность, а не работа.

### 0-D. Две колонки сразу (сумма **и** среднее), полоса — по среднему

Что: 0-B + колонка суммы «для справки», без полосы.
Цена: +1 колонка.
Риск: сумма рядом с полосой от среднего читается как «полоса не про эту
цифру»; провоцирует вопрос «почему сумма 3.4, а режим „тяжёлый“ при пороге 3».

**Рекомендация: 0-B.** Причина — только 621 из 3 348 групп-недель (18.5 %)
имеют n ≥ 2, а сумма меняет смысл КОИ (безразмерная интенсивность ≠ объём).
Витрина остаётся честной: «сколько упражнений, какие цифры, какая типичная
интенсивность», объём — в тоннаже.

## 3. Развилка A. Нормализация push-up/pull-up

Премиса опровергнута (§1.1), поэтому «обязательной» опции здесь нет — есть
цена и риск каждой.

### A0. Не нормализовать; сказать, чего в КОИ нет ★ рекомендация

Что: в подпись витрины (и в докстринг `weekly_koi`) добавить факт: «своё тело
без добавки (вес = 0) и упражнения без 1RM (`ПРЕСС`, `ПОДЪЁМ НОГ`, `ПЛАНКА`,
`КАРДИО`) в КОИ не входят — у них нет базы 1RM». 16 групп из 20.
Цена: 2 строки текста + 2 теста на текст (нет/есть), 0 изменений данных.
Риск: объём своего тела остаётся невидимым **в КОИ** (но виден в тоннаже и
подходах `health/groups.py`); пользователь может прочесть «нет строки» как
«не тренировал».

### A1. Включить «только тело» через оценку веса тела

Что: для строк с `weight = None` подставлять вес тела по годам
(`etl.bodyweight_map`), пересчитать `rm_ma_30d` и `koi`, перегон метрик +
снимок источника.
Цена: ~**146** строк `vest_only` получают вес (плюс несколько строк
`total_bodyweight` без веса) — это **маленькая** правка данных, но каскад
широкий: `sets.weight` меняется → тоннаж по группам (`health/groups.py`),
`weekly_tonnage`/`cum_tonnage` в `ml_features`, ACWR — всё это уже не
«витрина». Снапшот, перегон, сверка «до/после» по всем витринам.
Риск: вес тела — **годовая оценка**, не измерение; КОИ останется в масштабе
(по замеру `w/RM` у `vest_only` 0.82, cap не сработает — 0 случаев), то есть
числа появятся, но на оценке. Риск второй: 1 143 подхода пресса/планки всё
равно останутся без КОИ (это решение таксономии, а не отсутствие веса) — «своё
тело в групповом КОИ» станет полным лишь на бумаге. Риск третий: тоннаж
отжиманий/подтягиваний начнёт считаться в кг и смешается с железом в
`health/groups.py` — это правка смысла существующей витрины, а не 4.3.

### A2. Отдельная дорожка «своё тело» (режим в строке витрины)

Что: колонка `режим` (`iron` / `своё тело`) в витрине, без смешивания в
среднем.
Цена: +1 колонка, +1 фильтр, ~20 строк, 3–4 теста.
Риск: строк вдвое больше; среднее по дорожке «своё тело» считается по 1–2
упражнениям (Подтягивания, Брусья, Отжимания) — шум; полоса по среднему всё
равно смешивает внутри дорожки.

### A3. Нормировка «доля от своей нормы» (`koi_week / медиана упражнения`)

Что: безразмерная величина, 1.0 = «неделя как обычно»; сумма/среднее по группе
сравнимы между упражнениями по построению.
Цена: новый смысл полос (нужны свои пороги — развилка B3), причинная медиана:
считать её **только по прошлым неделям** (иначе взгляд в будущее, запрещённый
правилом проекта) → скользящая медиана, ~40 строк + тесты.
Риск: самореферентность — у упражнения с 3 неделями медиана нестабильна;
«тяжёлая неделя» перестаёт быть абсолютной величиной и становится «выше
своей нормы»; сравнение между людьми/годами ломается.

**Рекомендация: A0.** Замер не даёт мотива пересчитывать; цена A1 — перегон
данных и ML ради нулевого прироста КОИ; A3 меняет смысл шкалы.

## 4. Развилка B. Пересчёт полос `KOI_BANDS_WEEK`

### B0. Новых констант не вводить; полоса — по среднему, старые пороги ★ рекомендация

Что: `KOI_BANDS_WEEK` не трогаем; если витрина 0-B, полоса группы считается по
среднему (медиана 1.22, >4 — 1.7 %, то есть практически как по упражнению).
Цена: 0 новых констант, 0 правок `core.py`.
Риск: полосы остаются «упражненческими» по смыслу; на группе из 3 упражнений
среднее может скрыть одну тяжёлую сессию (её видно в колонке `КОИ макс`).

### B1. Новые абсолютные константы под сумму (`KOI_BANDS_WEEK_GROUP`)

Что: пороги из замера: **1.4 / 1.9 / 3.0** (это q50/q75/q90 распределения
группа-недель), `> 3.0` — «Вы сошли с ума??» (4.7 % строк).
Цена: 1 константа в `core.py` + 1 рендер + тест на границы, ~25 строк.
Риск: **пороги выведены из своей же истории** — «очень тяжёлая» становится
определением «топ-10 % моих недель», а подаётся как абсолютная шкала; при росте
данных (2 новых года) границы уплывут, а константа останется — расхождение
будет тихим. Плюс сумма запрещена докстрингом `weekly_koi`.

### B2. Сумма в колонке, полоса — по `сумма / n`

Что: то же, что 0-D, но формально: агрегат хранит сумму и n, полоса считается
от среднего.
Цена: +1 колонка.
Риск: см. 0-D — рядом стоящие «сумма 3.4» и «режим: тяжёлый (порог 3)» читаются
как ошибка.

### B3. Пороги для «доли от своей нормы» (нужен A3)

Что: три новых порога (например `0.5 / 1.0 / 1.5` — «недогруз / как обычно /
выше нормы») и отдельные подписи.
Цена: A3 + 3 константы + причинная медиана.
Риск: зависит от A3 целиком; пороги относительные, их нельзя сравнивать с
дневными `KOI_BANDS`.

**Рекомендация: B0.** Пересчёт полос — следствие выбора «сумма»; при
рекомендованном 0-B он не нужен. Если владелец выберет 0-C, то B1 — цена
известна (1 константа, пороги 1.4/1.9/3.0, самореферентность подписать).

## 5. Что остаётся нетронутым (при любом решении)

* `sets.koi`, `sets.rm_ma_30d`, `sets.weight` — **никаких** пересчётов;
* `v_weekly_koi`, `v_session_koi` — не меняются (новый вид **читает** их);
* `core.KOI_BANDS`, `core.KOI_BANDS_WEEK` — при 0-B/B0 не меняются;
* `health/groups.py` (тоннаж/подходы/время по группам) — не дублируется и не
  правится; КОИ-витрина рядом, а не вместо;
* `ml_features`/`ml_labels`/`ml_score`, гейт, состояние, дайджест,
  рекомендация — не трогаются (КОИ — читаемая витрина, решений не двигает);
* таксономия и `WEIGHT_MODE_OVERRIDE` — не трогаются; веса участия (4.2) не
  вводятся: группа = **одна** на упражнение (`exercise_group`), без долей.

**Граница с 4.2:** 4.3 не имеет права вводить «жим → грудь 0.6 / трицепс 0.3».
Когда 4.2 появится, вид можно расширить до участвующих мышц — но не раньше и
не «на всякий случай».

## 7. Тесты-кандидаты (свойства, не константы — правило W7-(g))

1. `n = 1` → `koi_mean == koi_max == koi_week` (одиночная группа-неделя не
   искажается агрегатом).
2. `koi_mean` лежит в `[min, max]` по упражнениям группы-недели.
3. `exercises` равно числу строк `v_weekly_koi` этой группы-недели; сумма
   `exercises` по всем группам-неделям равна числу строк `v_weekly_koi`.
4. Полоса по среднему = `KOI_BANDS_WEEK` от `koi_mean` (границы 2/3/4
   проверяются на синтетике: 1.99→Лёгкий, 2.0→Тяжёлый, 3.99→Очень тяжёлый,
   4.0→«Вы сошли с ума??»).
5. Группы `NO_RM_GROUPS` не появляются в агрегате, и подпись это говорит.
6. `--group` в агрегате фильтрует по группе; `--exercise` + `--by-group` —
   ошибка argparse (взаимоисключение).
7. Живые свойства: число группа-недель = 3 348 на текущей базе **не** пинуется;
   пинуется инвариант `SUM(exercises) == COUNT(*) FROM v_weekly_koi`.
8. Подпись не содержит стрелок и порогов, которых нет в `core.py` (урок E4).

Ожидаемая дельта прогона: **+10…14 тестов** к текущим 853.

## 9. Замеры: как воспроизвести

Все числа получены read-only по `sql/training.db` (20 995 подходов, 441 неделя,
99 упражнений, 16 групп).

```sql
-- 1. масштаб КОИ по режимам
SELECT weight_mode, COUNT(*) n,
       SUM(koi IS NOT NULL) with_koi,
       AVG(weight / rm_ma_30d) ratio_mean
  FROM sets
 WHERE rm_ma_30d IS NOT NULL AND weight > 0
 GROUP BY weight_mode;

-- 2. почему vest_only без КОИ (кучи непересекающиеся: сначала NO_RM)
--    сумма = 1309; важное: rm_ma_30d — колонка упражнения, не строки
-- 2.1
SELECT COUNT(*) FROM sets WHERE weight_mode = 'vest_only'
  AND skipped = 0 AND is_timed = 0 AND koi IS NULL
  AND exercise_group IN ('ПРЕСС', 'ПОДЪЁМ НОГ', 'ПЛАНКА', 'КАРДИО');   -- 1143
-- 2.2 (NOT IN те же четыре)
SELECT COUNT(*) FROM sets WHERE weight_mode = 'vest_only'
  AND skipped = 0 AND is_timed = 0 AND koi IS NULL
  AND exercise_group NOT IN ('ПРЕСС', 'ПОДЪЁМ НОГ', 'ПЛАНКА', 'КАРДИО')
  AND weight IS NULL;                                                   -- 146
-- 2.3
SELECT COUNT(*) FROM sets WHERE weight_mode = 'vest_only'
  AND skipped = 0 AND is_timed = 0 AND koi IS NULL
  AND exercise_group NOT IN ('ПРЕСС', 'ПОДЪЁМ НОГ', 'ПЛАНКА', 'КАРДИО')
  AND weight IS NOT NULL AND rm_ma_30d IS NULL;                         -- 20
-- 2.4 (cap)                                                        -- 0

-- 3. недельные суммы по упражнению
SELECT MIN(koi_week), MAX(koi_week), AVG(koi_week), COUNT(*) FROM v_weekly_koi;

-- 4. группа × неделя: сумма, число упражнений, сумма минус максимум
SELECT week, exercise_group, COUNT(*) n,
       SUM(koi_week) s, MAX(koi_week) m
  FROM v_weekly_koi GROUP BY week, exercise_group;

-- 5. упражнения на группу-неделю: медиана 1, q90 2, max 4
SELECT n, COUNT(*) FROM (
  SELECT week, exercise_group, COUNT(*) n
    FROM v_weekly_koi GROUP BY week, exercise_group) GROUP BY n;
```

# koilog

`koilog` — разбор журнала силовых тренировок в одну базу SQLite и расчёт
производных метрик: 1RM, рекорд, динамика, скользящее среднее и КОИ
(«коэффициент относительной интенсивности»). Поверх базы строится программа роста
нагрузки — только по тем весам, которые есть в наличии в зале.

Название — от КОИ и `log`: журнал, который считает КОИ.

Ядро `koilog` и подпакет `koilog.health` (разбор Apple Health, нагрузка, метки
болезни) держатся на стандартной библиотеке Python 3.13. `matplotlib` и
`ipywidgets` нужны только ноутбукам, а `numpy`/`scikit-learn` — только
ML-разделу `koilog.health` (extra `ml`), и ни одна обычная команда
`python -m koilog` их не требует.

## Быстрый старт

```
python -m koilog load                       # разобрать оба CSV в sql/training.db
python -m koilog stats                      # сводка по упражнениям за 3 месяца
python -m koilog stats --all                # вся история
python -m koilog plan "Жим гантелей"        # программа + переходы + периоды
python -m koilog weeks                      # недельные суммы КОИ по упражнениям
python -m koilog history "Отжимания" --from 2026-01-01 --to 2026-10-08
python -m koilog history "Отжимания" --reverse   # от последней даты к первой
python -m koilog explain "Отжимания"        # разбор парсинга и расчёта
python -m koilog check                      # что в данных требует решения
python -m koilog outliers                   # разбор выбросов по правилам
python -m koilog export                     # выгрузка таблицы sets в CSV

python -m koilog refresh --deep             # весь конвейер часов разом
python -m koilog apple-load                 # разобрать выгрузку Apple Health
python -m koilog health-load                # внешняя нагрузка + дни здоровья
python -m koilog illness                    # эпизоды болезни по уровням
python -m koilog return                     # возврат к весам: кривая, рампа, гейт
python -m koilog digest                     # день одной карточкой
python -m koilog ml                         # признаки, CV, красный флаг (extra ml)
```

Тесты:

```
python -m unittest discover -s tests
```

`load` занимает около минуты: 21 тысяча подходов, несколько проходов оконных
функций по всей таблице и второй проход с пересчётом веса тела. Загрузка
**пересобирает каждый переданный источник целиком**: строки этого источника
удаляются и вставляются заново, поэтому переэкспорт с другой нумерацией строк
не оставляет в базе задвоенных подходов.

## Что внутри

```
koilog/core.py        формулы 1RM и КОИ, программа роста нагрузки  (без БД)
koilog/taxonomy.py    124 имени упражнений -> 20 групп, режимы записи веса
koilog/equipment.py   инвентарь зала: какие веса вообще можно поставить
koilog/rules.py       пороги и правила проверки записей
koilog/etl.py         разбор CSV, схема, метрики, отчёты о качестве
koilog/stats.py       статистика, история, объяснение расчёта, программа, периоды
koilog/health/        Apple Watch + нагрузка + болезни (подпакет)
  apple.py            разбор export.xml в таблицы aw_*
  load.py             внешняя нагрузка: ACWR, sRPE, монотонность, стрейн
  illness.py          метки эпизодов: confirmed / probable / gap_only
  ml.py               признаки и модели (extra ml; без numpy не работает)
  analysis.py         готовые срезы рядов для ноутбука
  retrain.py          возврат к весам: детрейн-кривая, рампа, гейт
  digest.py           дневной дайджест: каналы, нагрузка, рекомендация
  text.py             табличное оформление CLI и ноутбука
koilog/cli.py         командный интерфейс
```

`core.py` ничего не знает про SQLite и CSV — поэтому вся математика
тестируется без базы. `taxonomy.py` — единственное место, где живёт знание об
упражнениях; `equipment.py` — единственное место, где живёт знание о снарядах.
Новые выгрузки и новый зал не требуют правок кода.

`koilog.ipynb` — обзор поверх той же базы: он импортирует те же функции, что и
CLI, поэтому вывод в ноутбуке и в терминале не расходится. Внутри — словарь
колонок, сводка за окно, программа, недельные суммы КОИ, история упражнения за
заданный интервал, разбор расчёта «от сырого значения до КОИ» и интерактивный
график 1RM (выпадающий список упражнений и два поля дат; с `ipywidgets` он
интерактивный, без них рисуется один статичный).

Файлы: `data/journal.csv` и `data/report.csv` — по одному источнику на файл.
Старые имена `journal-export.csv` и `report-export.csv` принимаются как
запасные, если новых нет. Внутри базы источник называется `journal` или

124 упражнения, 20 групп; 1RM считается для 16 671 подхода. Остальные — своё

подъём ног, планка, кардио).

11 дат встречаются в обоих источниках. Журнал подробнее, поэтому в эти дни
берётся он, а строки отчёта пропускаются.

## Формулы и производные колонки

**1RM** — Brzycki, `вес × 36 / (37 − повторы)`. Формула валидна примерно до
10–12 повторов, поэтому выше `RM_MAX_REPS = 20` 1RM не считается вовсе.

Производные колонки считаются в SQL, несколькими проходами:

| колонка | что значит |
|---|---|
| `rm` | 1RM отдельного подхода |
| `rm_session` | лучший подход упражнения за тренировку |
| `rm_delta` | `rm_session` минус `rm_session` предыдущей тренировки по этому же упражнению |
| `rm_ma_30d` | скользящее среднее `rm_session` за 30 календарных дней **по упражнению** |
| `koi` | `повторы / (1 − вес / rm_ma_30d) / 100` |

**КОИ** — мера усталостной нагрузки: `Σ повторы / (100 − интенсивность%)`, где
интенсивность = `вес / база 1RM`. Интенсивность — доля, а формула выведена в
процентах, поэтому результат делится на 100: 6 повторов при 60 % дают 0,15, а
не 15. Выше 98 % от базы КОИ не считается вовсе — при интенсивности около 100 %
знаменатель уходит в ноль, и число определяется округлением, а не нагрузкой.

КОИ считается **по каждому упражнению отдельно**, а не по группе: у жима и
тяги в одной группе разные базы 1RM, и общая сумма теряет масштаб. Поэтому и
недельные суммы (`v_weekly_koi`), и суммы за тренировку (`v_session_koi`) —
по упражнениям.

Пропущенный подход, подход на времени и подход, помеченный правилом как
выброс, не попадают ни в 1RM за тренировку, ни в дельту, ни в скользящее
среднее, ни в КОИ.

## Режимы записи веса

Вес тела нигде не выгружается, и два источника писали его по-разному. Поэтому
режим объявлен явно на каждое упражнение (`taxonomy.WEIGHT_MODE_OVERRIDE`):

| режим | что записано | пример |
|---|---|---|
| `ABSOLUTE` | вес как есть | почти все упражнения со штангой и тренажёрами |
| `VEST_ONLY` | только добавка, своё тело прибавляем | `Отжимания` 0…20 |
| `TOTAL_BODYWEIGHT` | суммарный вес тела с добавкой | `Подтягивания` 67…82, `Брусья` 68…110 |

Одной конвенции на группу не хватает: внутри группы `ОТЖИМАНИЯ` отчёт пишет
`Отжимания от пола` как 0/25/45 (жилет), а `Отжимания на брусьях` как 65–86
(уже суммарный вес тела). Ошибка здесь стоила бы +70 кг на 370 реальных
подходах.

### Вес тела по годам

Константы 70 в расчётах нет. Вес тела оценивается из записей
`total_bodyweight` по каждому году отдельно, в два шага.

**Шаг 1 — «чистый пол», иначе мода, по каждому упражнению внутри года.**
Сырой минимум бывает весом снаряда (25 кг в 2018), поэтому одного минимума
недостаточно — но и одна мода бывает неправа: в 2026 мода подтягиваний 78 при
112 подходах — это почти всегда жилет, а нижняя граница в 70 кг стоит 28
подходов из 112. Нижнее значение упражнения-года берётся, только если оно
**плотное**: не меньше 5 подходов и не меньше 20 % подходов этого упражнения за
год.

**Шаг 2 — расхождение между упражнениями года разрешается вниз** — жилет
добавляет вес, поэтому верный ответ нижний кластер.

Получилось 70 (2015), 68 (2016), 67,7 (2017), 67,4 (2018), 69 (2019 и 2020),
68 (2021–2023), 68 (2024), 70 (2025 и 2026).

Оценку видно в `python -m koilog check` и в начале вывода `python -m koilog load`.
Переопределить:

```
python -m koilog load --bodyweight 68                      # для всех лет сразу
python -m koilog load --bodyweight-year 2021=82            # только 2021
python -m koilog load --bodyweight-year 2021=none          # вернуть год к оценке
```

## Правила проверки записей

Пороги объявлены явно в `koilog/rules.py`, применяются к **записанному** весу и
никогда не переписывают его. Нарушение не удаляет строку: строка остаётся в
базе и в выгрузке, но получает `is_outlier` и `outlier_rule` и не участвует в
1RM, дельте, скользящем среднем, КОИ, объёме, статистике и программе.

| правило | порог | что означает |
|---|---|---|
| `seconds_in_weight` | > 20 кг | в упражнении «на своём теле без веса» это секунды |
| `pushups_max` | > 20 кг | в отжиманиях это попытка посчитать % веса тела, а не жилет |
| `bodyweight_max` | > 100 кг | суммарный вес тела; к штанге правило не относится |
| `reps_max` | > 30 повторов | больше 30 повторов в подходе не бывает |

`seconds_in_weight` — единственное правило, которое меняет саму запись, а не
помечает её: подходы «подъём ног в висе» и «планка», где вместо секунд
записан вес, переносятся в `time_seconds`. Поэтому в отчёте они идут отдельным
блоком и не называются выбросами.

Подробный разбор — `python -m koilog outliers` (`--rule`, `--limit`, `--csv`).

## Инвентарь зала

`koilog/equipment.py` — единственный источник правды о том, что можно
поставить. Программа не предложит вес, которого нет в инвентаре.

Гантели — **ровно 16 пар на руку**: 5, 7, 9, 11, 13, 15, 18, 22, 25, 27,
29, 32, 34, 36, 38, 40 кг. Для упражнения двумя руками лестница — удвоенная
(10…80 кг суммарных), для одной гантели — сама пара.

Плиты тренажёров заданы типовыми лестницами (шаг 20 lb / 4,54 кг и другие). Они
помечены как приблизительные: это набор «похожих», а не паспорт конкретного
тренажёра.

Жилета в зале, судя по журналу, нет — поэтому по умолчанию программа предлагает
только «своё тело». Жилет 0…20 кг с шагом 2 включается флагом:

```
python -m koilog plan "Отжимания" --vest
python -m koilog plan "Подтягивания на перекладине" --vest   # лестница «тело + жилет»
```

Вес, который записан в журнале, но которого нет в инвентаре, **не
переписывается**: подход остаётся настоящим, он просто не может быть предложен
вперёд, а программа стартует с ближайшего не тяжелее и отмечает это строкой
`~`. Такие веса собираются в блоке «ВЕСА, КОТОРЫХ НЕТ В ИНВЕНТАРЕ» в `check` и
`outliers`.

## Пресс, подъём ног, планка, кардио

Группы `ПРЕСС`, `ПОДЪЁМ НОГ`, `ПЛАНКА`, `КАРДИО` не получают ни 1RM, ни КОИ:
для них нет осмысленной базы, а прибавлять вес тела к весу тренажёра значит
выдумать суммарный вес, которого никто не записывал. Записанный вес у таких
упражнений остаётся как есть.

## Статистика

`python -m koilog stats` по умолчанию показывает **последние три месяца от
последней тренировки** — нет смысла смотреть упражнение, которым давно не
занимались. Вывод заканчивается строкой вида

```
окно: последние 3 мес. до последней тренировки, с 2026-07-08
показано 15 из 124 упражнений (вся история - ключ --all)
```

Колонки таблицы:

| колонка | что значит |
|---|---|
| подх | подходов упражнения в окне |
| лучший | лучший 1RM **внутри окна** |
| рекорд | лучший 1RM за **всю историю** |
| посл. | 1RM последней тренировки в окне |
| Δ к рекорду | `посл. − рекорд`: 0 = на рекорде, минус = отставание |
| МА30 | скользящее среднее 1RM за 30 дней по упражнению (база КОИ) |
| объём | сумма `вес × повторы`, в килограммо-повторах |

```
python -m koilog stats                  # окно 3 месяца (по умолчанию)
python -m koilog stats --months 6       # своё окно
python -m koilog stats --all            # вся история
python -m koilog stats --csv            # то же в CSV
```

### История упражнения

`python -m koilog history "УПРАЖНЕНИЕ"` печатает таблицу по тренировкам: лучший
подход, число подходов, объём, 1RM тренировки, дельту к предыдущей тренировке и
КОИ. Интервал задаётся ключами `--from` и `--to` (ISO-даты, **обе включительно**;
любой можно опустить — тогда границы нет). Пустой интервал с обеих сторон — вся
история упражнения. По умолчанию строки идут от первой даты к последней; флаг
`--reverse` разворачивает порядок, и тогда `--limit` оставляет самые свежие
тренировки.

```
python -m koilog history "Отжимания" --from 2026-01-01 --to 2026-10-08
python -m koilog history "Отжимания" --limit 0      # вся история, все тренировки
python -m koilog history "Отжимания" --limit 20 --reverse   # 20 последних
```

### Недельные суммы КОИ

`python -m koilog weeks` печатает по одной строке на пару «неделя, упражнение»:
число подходов, сумму КОИ за неделю и режим. Неделя — календарная **ISO 8601**
(`%G-W%V`, понедельник–воскресенье), поэтому метка совпадает с приложениями и не
рвётся на стыке года. КОИ считается по каждому упражнению
отдельно, поэтому суммы разных упражнений не складываются. Режим определяется по
**недельной сумме** (`core.KOI_BANDS_WEEK`): меньше 2 — лёгкая неделя, 2…3 —
тяжёлая, 3…4 — очень тяжёлая, больше 4 — «Вы сошли с ума??». Фильтры: `--exercise`,
`--group`, `--limit`.

### Разбор расчёта

`python -m koilog explain "УПРАЖНЕНИЕ"` отвечает на вопрос «откуда это число».
Сначала печатает, как читаются выгрузки (кодировка, разделитель, приоритет дат,
правила) с путями относительно корня проекта, затем — сводку по упражнению
(источники, режимы веса, период, сработавшие правила) и последние подходы во всей
цепочке: `сырой вес → режим → свой вес + добавка → суммарный вес → 1RM →
1RM тренировки → Δ → МА30 → КОИ → полоса`. Отдельная колонка `разм` помечает
разминочные подходы (в 1RM и КОИ они не входят).

## Программа и периоды

`python -m koilog plan "…"` печатает программу роста нагрузки, следом — переходы
на следующий вес, а под ними четыре скользящих окна от последней тренировки по
упражнению: месяц, квартал, полугодие, год. По каждому — тренировки, подходы,
объём, лучший 1RM, изменение 1RM к предыдущему окну той же длины и средний КОИ на
подход. Дальше идут два ASCII-графика: изменение 1RM и объём.

В шапке программы видно рекорд, изменение к прошлой тренировке (с её датой) и
МА30. Графики рисуются знаками — `matplotlib` в зависимостях пакета не
числится. Кому ASCII не годится, у того есть числа:

```
python -m koilog plan "Жим штанг" --csv
```

По умолчанию каждый новый вес в программе начинается с 6 повторов («волна со
сбросом»). Подбор максимума повторов на новом весе включается флагом
`--optimal-reps` и по умолчанию выключен.

Проверка «повысить вес» и добавление повтора выполняются **только после
выравнивания повторов по всем рабочим подходам**: пока подходы не равны,
проходит лишь сдвиг волны. Поэтому рост повторов медленный, а горизонт
программы по умолчанию 18 шагов (`--steps`, чтобы увидеть два-три перехода на
новый вес).

## Нагрузка, часы Apple Watch и болезни

Подпакет `koilog.health` добавляет вторую половину картины: не «сколько я
поднял» (внешняя нагрузка), а «как организм ответил» (внутренняя нагрузка —
ночной пульс, ВСР, дыхание, температура запястья, сон из Apple Watch). Болезнь
здесь — исход, который связывается с расбалансом между нагрузкой и
восстановлением.

```
python -m koilog refresh    # весь конвейер разом; --deep добавляет ML-блок
python -m koilog apple-load    # разобрать выгрузку Apple Health в таблицы aw_*
python -m koilog health-load   # внешняя нагрузка: load_daily, health_days
python -m koilog illness       # метки эпизодов: confirmed / probable / gap_only
python -m koilog return        # возврат к весам: кривая, рампа, гейт
python -m koilog digest        # день одной карточкой: каналы, нагрузка, совет
python -m koilog ml            # признаки, CV-отчёт, красный флаг (extra ml)
python -m koilog ml --lag      # + лаг-анализ признаков (0-21 дн)
```

`refresh` гонит конвейер целиком и **в правильном порядке** — выгрузка →
нагрузка → календарь → эпизоды (→ ML-блок с `--deep`) — и печатает свежесть
по каждой таблице, чтобы отставание было видно сразу, а не вычислялось вручную.
Разбор гигабайтного архива (~45 с) скипается, если файл не менялся: после
успешной загрузки в `aw_meta` пишется слепок «mtime + размер», и следующий
запуск занимает доли секунды; слепок не записывается, если разбор упал.

`apple-load` читает выгрузку **прямо из архива** `data/*.zip` (или из
`export.xml`, если он распакован) одним проходом `iterparse`: файл около
гигабайта, в память целиком не влезает. `--xml` принимает XML, папку выгрузки
или архив; без него берётся самый свежий архив в `data/` — распаковывать его
не нужно. Из архива же читаются ЭКГ (`ecg_*.csv`); `export_cda.xml`
отбрасывается. Полезное окно
— **с 2024-01-16**: раньше часы пишут только пульс покоя и сон, без ВСР/ЧДД/
температуры, поэтому в анализ они не идут. Источник фильтруется: пульс покоя,
ВСР, дыхание, SpO2 и температуру запястья пишет только Apple Watch (выгрузка
записывает имя с неразрывным пробелом — это учтено).

Команда `health-load` (имя `load` занято разбором CSV) считает **внешнюю
нагрузку** (`health/load.py`, только стандартная библиотека): тоннаж,
sRPE-суррогат, ACWR и его EWMA-версия, монотонность и стрейн (Foster), регресс
e1RM. Календарь непрерывный: дни отдыха — нули, а не пропуски.

**Метки болезни** (`health/illness.py`) трёхуровневые:

| уровень | как ставится |
|---|---|
| `confirmed` | ручная температура ≥37,5 °C **или** ≥2 нарушенных канала за день |
| `probable` | одиночный сильный сигнал **автономного ядра** (RHR ↑ или ВСР ↓ при z>3); либо перерыв 14–30 дней с отклонением часов |
| `gap_only` | только перерыв в тренировках ≥14 дней без физиологии; в обучение не идёт и отчитывается отдельно |

z-скоры считаются к личному фону за предыдущие 60 дней (минимум 14
наблюдений, текущий день не входит): RHR >2, ВСР <−2, ЧДД >2, температура
запястья >2,5. Одиночный сильный сигнал засчитывается **только по RHR/ВСР**:
ЧДД (SD ≈ 0,77) и температура запястья (SD ≈ 0,29) на обычных днях шумят
сильнее сигнатуры, поэтому их выброс эпизод не открывает — они лишь
подтверждают при ≥2 метриках.

**ML** (`health/ml.py`) — необязательный extra:

```
pip install "koilog[ml]"       # numpy + scikit-learn
```

Протокол — **leave-one-episode-out** (случайные складки запрещены: временная
течь). **Честная оговорка:** эпизодов около трёх десятков за два года, это
проверка гипотезы, а не реальный предиктор; при таком n p-value был бы
самообманом, поэтому их нет.

Три постановки (§9.1):

- **v1, day-классификация** — «болезнь начнётся за 14 дней»; метрики: recall
  эпизода и ложные срабатывания в месяц. Бейзлайн: ловит почти всё, потому что
  алертить можно каждый день.
- **v2, «риск на горизонте»** — дискретная выживаемость в landmark-форме:
  `P(onset в (t, t+7] | жив на t)`; дни внутри эпизодов из обучения исключены
  (`at_risk`). Метрики событийные: **lead time** первого алерта, поимка
  эпизодов с lead ≥ 3 дня, ложные алерты в месяц. Признаки v2 добавляют к
  основным тренды и разрывы серии: `hrv_slope3/5`, `rhr_slope3/5`,
  `cum_tonnage_10/21`, `days_since_training`, `gap_14`, «долг × тоннаж за 21
  день». Буквальный h(t) не берётся: признаки самого дня t (ВСР уже подняты)
  учат модель предсказывать «сегодня болен», а не «через 3–5 дней».
- **честная оценка** — `walk_forward()` прогнозирует день за днём **только по
  прошлому**, а дефолтный порог `0.5` (для `class_weight=balanced` он ничего не
  значит) заменён на operating point: порог = квантиль прошлых вероятностей под
  бюджет `b ∈ {2, 4, 8}` алерт-дней в месяц. Recall@бюджет сравнивается с двумя
  нулями — **случайным алертом того же размера** и **сезонным календарём**
  (зима). `matched_auc()` считает AUC против далёкого контроля (15–28 дней до
  начала) с **bootstrap-CI по эпизодам**: дни одного эпизода не независимы, и
  наивный по дням интервал был бы ложно узким.

Результат на реальных данных (33 эпизода, разметка с привязкой к ближайшему
будущему началу эпизода). Сначала знаменатель: **уловимых эпизодов 23 из 33** —
7 неуловимы вовсе (их `lead ≥ 3`-окно целиком внутри болезни соседнего
эпизода: 2024-02-18, 2024-03-04, 2025-03-16, 2026-01-03, 2026-02-15,
2026-02-24, 2026-08-12), ещё 3 пришлись на первые дни ряда, где модели ещё не
на чем учиться. Поэтому recall@бюджет делится на уловимые; «потолок»
(«алертить всё») равен 0,79 по всем 33 эпизодам и 1,00 по уловимым.

**Отрицательные результаты** (зафиксированы, чтобы за ними не охотиться
повторно):

- **Недельного предиктора нет**: recall@бюджет при `lead ≥ 3` на всех трёх
  бюджетах равен случайному алерту той же частоты — 0,09 / 0,22 / 0,61
  против 0,05 / 0,22 / 0,60 при 0,4 / 1,6 / 5,6 алерта в месяц.
- **Гипотеза «сигнатура живёт за 10–21 день» не подтверждена**: AUC против
  далёкого контроля (15–28 дней до начала) 0,575 [0,475, 0,677] — интервал
  накрывает 0,5. Доработки оценки этой гипотезе не помогут: соревнование
  шло с нулями, а они уже пойманы.
- **Сезонный календарь проигрывает случайному**: 0,22 против 0,60 при почти
  равном бюджете, потому что эпизоды распределены почти равномерно —
  зимних стартов 13 из 33, зимний календарь физически не может поймать две
  трети эпизодов, а случайный алерт той же частоты распределён по году.
- Walk-forward AUC 0,652 [0,563, 0,737] держится целиком на продроме:
  **0,764 [0,666, 0,852]** при `lead` 1–2 против **0,588 [0,491, 0,682]** при
  `lead` ≥ 3. Это «болезнь уже началась», а не предупреждение — обратная
  причинность (болезнь срывает тренировки, см. лаг-анализ).

**Положительный результат — nowcast.** Алерт за 1–2 дня до начала при том же
числе алертов в месяц: 0,03 / 0,28 / 0,59 против случайного 0,02 / 0,11 /
0,34. Разница против случайного (эпизодный bootstrap): +0,01 [−0,02, +0,08] /
**+0,14 [+0,01, +0,28]** / +0,21 [+0,06, +0,38] — на среднем бюджете интервал
не накрывает ноль, то есть поимка продрома отличается от случайного алерта
той же частоты (на самом дешёвом бюджете разницы пока нет). Продукт из этого —
детектор «эпизод, судя по всему, начался» (отменить тяжёлую сессию, измерить
температуру), а не предупреждение за неделю.

Ложные срабатывания считаются **только бюджетно**: порог 0.5 не operating
point, поэтому колонки «ложн./мес» из таблиц отчёта убраны вовсе, а не
оставлены «справочно» — рядом с бюджетными числами это магнит для ложных
сравнений.

Честный вывод: предупреждения за неделю нет — есть детектор продрома за 1–2
дня и дисциплина бюджета алертов. «Рисковый месяц» по нагрузке остаётся
гипотезой, которую подтвердит только расширение выборки (§9.2–§9.4 отложены на
раунд 6).

`koilog-health.ipynb` — витрина поверх той же базы: покрытие часов по годам,
симптомная сигнатура на подтверждённых эпизодах, спагетти-графики 28 дней до
эпизода с контрольными окнами, лаг-анализ, персональные квантили и ML-отчёт.

Материал опирается на: Impellizzeri 2019 (внутренняя нагрузка), Gabbett (ACWR),
Williams 2017 (EWMA), Foster 1998 (монотонность и стрейн), Schoenfeld (объём),
Meeusen 2013 (красный флаг), Mishra 2020 / Quer 2021 / Radin 2020 (сигнатура
болезни).

### Возврат к рабочим весам после болезни

Когда болезнь прерывает цикл, сила у тренированных почти не падает 2–3 недели
(Mujika & Padilla 2000), но возвращаться надо от последнего «до болезни» рабочего
веса упражнения, а не от общего плана. Команда `return` печатает **сначала
расчёты** (рампу, разметку прошлых возвратов, гейт), а описательную
детрейн-кривую с литературными ориентирами — в конце: числа всегда на виду, а
ссылки под ними. Предболезненный вес — **лучший рабочий подход** последней
тренировки упражнения до эпизода, а не первый (разминочный).

```
python -m koilog return                     # по самому частому упражнению
python -m koilog return "Жим гантелей лежа" # по конкретному
python -m koilog return "…" --returns       # + разметка прошлых возвратов
python -m koilog return "…" --json
```

- **рампа** (`retrain.return_plan`): старт — верх 1-й недели, доля от
  предболезненного веса по длине простоя (`RAMP_TABLE`; таблица откалибрована
  по личному журналу: возврат сразу на ≥100 % ассоциирован с рецидивом
  болезни, 45 % против 10 %). Шаги считает `retrain.ramp_program`: один шаг =
  неделя, подходы внутри — «лесенка с перекрытием» (36/44/50 → 50/54/58),
  повторы подбираются так, чтобы КОИ тренировки остался в Optimal.
  Мощность/взрывные элементы — последними (Lepers 2024);
- **гейт** (`retrain.baseline_gate`): ВСР и RHR две ночи подряд в личном фоне
  ±1 SD, нет повышенной температуры запястья и активного эпизода. С симптомами
  тренироваться нельзя — риск вирусного миокардита;
- **разметка возвратов** (`retrain.returns`): скорость реампера в %/нед и
  рецидив — новый эпизод за 21 день. Возвраты делятся на «жёсткий / средний /
  мягкий». Выборка крошечная, это описание, а не доказательство (Bruusgaard
  2010; Nuzzo 2024; Raysmith & Drew 2016);
- **детрейн-кривая** (`retrain.detraining_curve`): по истории упражнения точки
  «простой → просадка e1RM» сводятся в бины `<7`, `7–14`, `14–28`, `>28` дней
  и печатаются в конце, рядом с литературными ориентирами. Это описание личных
  данных, а не доказательство.

### Дневной дайджест

Одна карточка дня сводит часы, нагрузку и рекомендацию:

```
python -m koilog digest                     # последний день с данными
python -m koilog digest --date 2026-10-17
python -m koilog digest --json
```

`digest` печатает z-каналы часов (RHR, ВСР, ЧДД, температура запястья, SpO2, сон)
против личного фона, состояние нагрузки (ACWR и его gap-aware версию,
монотонность, стрейн, недельный тоннаж, дней с последней тренировки) и **одну**
рекомендацию по приоритету: красный флаг недовосстановления (Meeusen 2013) →
покой (активный эпизод или гейт не пройден) → «завтра легко» (ЧДД, RHR и ВСР
отклонились вместе) → рампа (возврат после простоя, ACWR вздут) → «можно по
плану». Пустой `aw_daily` не запирает дайджест в «покой»: без физиологии
блокировать нечем.

## Известные ограничения

**1. Сумма КОИ растёт с числом подходов.** Полосы КОИ заданы именно для суммы:
недельные — в `core.KOI_BANDS_WEEK`, дневные — в `core.KOI_BANDS`. Недельные
суммы сравниваются по этим полосам, а не усредняются по подходам: усреднение
размывало бы границу «тяжёлая/очень тяжёлая неделя», которая в исходной логике
считается от суммы.

**2. 76 подходов в отчёте записаны весом жилета вместо суммарного веса.** Это
2018 год из выгрузки `report`: `Подтягивания` 25, 31,7, 37,3 кг при теле 67,4.
Эти строки не выброшены — правил для «слишком мало» нет, а выдумывать порог
значит выкидывать настоящие подходы. Они помечены в `check` как
неправдоподобная добавка.

**3. Свой вес в упражнениях с телом и жилетом завышает 1RM.** В отжиманиях на
руки действует лишь часть веса тела (примерно ⅔, а не 100 %), а в подтягиваниях
часть подходов записана только весом жилета (см. п. 2). Из-за этого e1RM
отжиманий выходит выше сравнимых жимов и плохо с ними сопоставим. Нужна доля
эффективной нагрузки по упражнению; пока `sets.weight` хранит буквально
записанный суммарный вес. Не реализовано.

**4. План «критическая нагрузка перед пропуском» не сделан.** Задумано было
отмечать нагрузку перед пропуском больше двух недель. Не реализовано.
